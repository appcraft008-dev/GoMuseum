Google Play Store Listing Experiments 需要**自然流量**才能分流。零曝光 ⇒ 零分流 ⇒ 无论跑多久都不会有结论。

> **所以本文件的正确读法**：它不是"下周要执行的计划"，是**放量当天就位的配置清单 + 判据**。把判据现在定死，是为了防止放量后拿到数据再回头找理由 —— 那样任何结果都能被解释成成功。
> ⛔ **不要在零流量时启动实验**：Play 的实验有最短运行期，空跑会占掉唯一的实验槽位（同一时间只能跑一个）。

## 1. Google Play Store Listing Experiments 能测什么

| 元素 | 可测 | 变体上限 |
|---|---|---|
| App icon | ✓ | 3 |
| Feature graphic | ✓ | 3 |
| Screenshots | ✓ | 3 |
| **Short description** | ✓ | 3 |
| **Full description** | ✓ | 3 |
| **Title** | ✗ | — |

> ⭐ 这是 Play 相对 iOS 的关键优势：**描述类字段可以 A/B**（iOS 的 PPO 不能）。但**标题不能测** —— 所以 `metadata-final-*.md` 里的 Title 推荐必须靠判断定下来，没有实验兜底。这也是为什么 Title 那三个版本的取舍理由写得比别处细。

## 2. 第一轮测试：核心定位（A/B）

| 项 | 内容 |
|---|---|
| **假设** | 如果 Slot 1 讲"你不需要知道它叫什么"（方向A·识别消除断点），商店页转化率会高于讲"一个 App 四家馆"（方向B·覆盖面），因为前者对应一个被竞品用户反复抱怨的真实断点（F5），后者只是功能说明 |
| **变量** | **仅 Slot 1 截图的主标题与构图**。其余 7 张、Feature Graphic、两段描述全部保持一致 |
| **对照组 (A)** | Slot 1 = `You don't need to know its name.` / FR `Pas besoin de connaître son titre.` |
| **变体 (B)** | Slot 1 = `Louvre, Orsay, Orangerie, Petit Palais — one app.` / FR 对应表达 |
| **目标用户** | Play 自然流量，en-US 与 fr-FR **分开跑两个实验**（两个市场的定位结论本就不同，合并会互相污染） |
| **主要指标** | Store Listing 转化率（页面访问 → 安装） |
| **次要指标** | 首次成功识别率、安装后首次识别耗时 |
| **最低运行周期** | 7 天**且** ≥1,000 次页面访问/变体（两个条件都满足才读数） |
| **胜出标准** | 转化率相对提升 ≥10% 且 Play 判定达显著；**同时**次要指标不出现 §4 定义的低质量增长信号 |
| **数据不足时** | 判为无结论，**保留 A 版**（有证据支撑的那版是默认值，不因"没测出来"就换） |
| **胜出版本会不会伤下游** | 方向B 若胜出需警惕：它吸引的是"想一次逛四馆"的用户，而我们四馆的讲解密度差异极大（Louvre 327 / Orangerie 18）。**若 B 胜出但 Orangerie/Petit Palais 的首次识别成功率显著低于 Louvre，应判为低质量增长** |

⚠️ **一次只改一个变量**。Play 同一时间只能跑一个实验，别把"改 Slot 1"和"改简短描述"塞进同一轮。

## 3. 后续测试候选（按优先级）

| 轮次 | 测什么 | 假设 | 主要指标 |
|---|---|---|---|
| 2 | **Short description**：`no title or number needed`（痛点）vs 既有稿（功能） | 讲痛点的版本转化更高 | CVR |
| 3 | **Feature graphic**：加副标题 `You don't need to know its name.` vs 现有纯标语 | 列表页第一视觉带上核心句能提高点入率 | 页面访问数（列表曝光 → 页面访问） |
| 4 | **Slot 2/3 顺序**：先"扫描中"再"结果页" vs 先"结果页"再"扫描中" | 先看到内容质量比先看到机制更能说服人 | CVR |
| 5 | **"4 家博物馆" vs "10 种语言"** 在 Slot 4 的表达 | 四馆比语言数更能打动巴黎游客 | CVR |
| 6 | **Full description** 开头两段顺序 | 痛点段前置 vs 产品段前置 | CVR |

每轮同样适用第 2 节的周期/显著性/数据不足处理规则。

## 4. 监测指标体系

### 4.1 商店侧（Play Console）

| 指标 | 用途 |
|---|---|
| Store listing acquisitions — **impressions** | 关键词布局是否带来曝光 |
| **Store listing visitors**（页面访问） | 图标 + 标题 + Feature Graphic 的点入力 |
| **Store listing conversion rate** | 截图与描述的说服力 —— **第一轮实验主指标** |
| **First-time installs** | 绝对量 |
| **Acquisition channel**（Play search / Play explore / third-party） | 区分 ASO 生效 vs 落地页导流 |
| **Search terms 报告** | ⭐ **唯一能证伪本轮关键词判断的真实数据源**。本轮所有"方向性判断"都等它来验 |
| en-US vs fr-FR 分市场 | 验证 F4 的市场差异结论 |

### 4.2 产品侧（埋点）

| 指标 | 定义 | 为什么必须看 |
|---|---|---|
| **首次成功识别率** | 安装后 7 天内至少成功识别 1 件 / 安装数 | scan-first 定位是否兑现。**这是整个定位的验证指标** |
| **安装后首次识别耗时** | 安装 → 第一次成功识别的中位耗时 | 激活摩擦 |
| **识别→播放讲解转化** | 识别成功后播放讲解的比例 | scan→listen 链路是否成立 |
| **识别命中 stub 的比例** | 识别成功但该件 `content_status=stub` | ⭐ **本轮新增**。实测 97.6% 藏品是 stub，这个比例直接决定"识别了却没讲解"的失望率 |
| 免费→付费转化率 | | 商业闭环 |
| **网络失败率** | 识别请求因网络失败的比例 | ⭐ **本轮新增**。F7：产品全程依赖网络而馆内网络实测很差 |
| 评分 / 评论数 / 反馈主题 | | 尤其盯"没有讲解""离线用不了"两类 |

### 4.3 低质量增长的判定（brief §十二 要求）

> **某版本提高了安装量，但触发以下任一条，判为低质量增长，不予采用：**
>
> 1. 首次成功识别率相对下降 ≥15%
> 2. 识别→播放讲解转化相对下降 ≥15%
> 3. 免费→付费转化率相对下降 ≥20%
> 4. **识别命中 stub 的比例相对上升 ≥15%**（说明文案把用户引向了我们没有内容的馆/品类）
> 5. 1–2 星评论中"没有讲解 / 识别不出来 / 没网用不了"主题占比上升

阈值说明：这些数字**是拍的，不是算的** —— 零基线状态下无法从数据推导。它们的作用是**在拿到数据之前先把线画好**，防止事后找补。拿到首批真实数据后应当重标定。
