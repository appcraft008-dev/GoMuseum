# GoMuseum 博物馆主文档（API 契约 + 内容体系 + 上馆手册 + 路线图）

> **这是唯一权威主文档。** 所有博物馆按本文的契约与路线图上线;奥赛 = 样板馆。
> **工作纪律**:每次决策 / 发现的问题 / 零散需求 → **回写本文**。带日期的 `docs/superpowers/specs/*` = 设计记录,**喂给本文**;本文永远是当前真相。新馆只读本文即可快速上线。
> 端点前缀 `/api/v1`。**加法/前向兼容**——只增字段、不破老解析;破坏性变更走版本化端点。
> 最近更新:2026-10-20(本地化完整性补记:静态表要测试强制配齐 + 十语逐字段验收查法;单值字段订正 + Wikidata 照抄原名;纪律 37 补记共享实体不许拿引用方兜底、权威覆盖也是覆盖)。此前:2026-10-14(P1-9B 深度段只写材料明说的;上新馆配方合并成一套;补 `/viewed` 端点;纪律 20 扩写、新增 53)。

## 北极星

上任意馆 = **配源 → 抓全证据包 → 生成一次(分层·去重·动态·接地)→ 封板**。馆上线后基本不再动,精力转下一个馆。本文 = 实现这一目标的契约 + 手册 + 路线图。

> 详细内容体系(三层体验 / 模块库 / 证据包)见 §内容体系;演进顺序见 §路线图。

## 端点总览

| 端点 | 用途 | 实现(`museum_repo.py`) |
|---|---|---|
| `GET /museums` | 馆索引(探索页) | `list_museums` |
| `GET /museums/{slug}?language=` | 完整馆包(元数据+分类+全藏品) | `get_museum_pack` |
| `GET /museums/{slug}/objects?...` | 分页藏品列表(列表页) | `list_objects` |
| `GET /museums/{slug}/objects/{qid}/content?language=` | 单件讲解(导览页) | `get_object_content` |
| `GET /search?q=&language=&limit=` | 全局搜索(探索页;跨馆藏品+博物馆) | `search/inprocess.py` |
| `GET /museums/{slug}/search?q=&language=&limit=` | 馆域搜索(馆列表页;只搜当前馆藏品) | `search/inprocess.py` |
| `GET /museums/{slug}/objects/{qid}/audio?language=&section=` | 懒 TTS(点播放才生成;返 `{audio_url}` R2 直链;生成中 409) | `endpoints/museums.py` |
| `GET /museums/{slug}/objects/{qid}/audio/stream?language=&section=` | 流式 TTS(✅2026-07-16 #256):首播边生成边播 | `endpoints/museums.py` |
| `POST /feedback` | 用户反馈(藏品级/App 级;匿名可写;204 无响应体) | `endpoints/feedback.py` |
| `POST /museums/{slug}/objects/{qid}/viewed` | 进讲解页打点(`content_viewed`;204,fire-and-forget) | `endpoints/museums.py` |

**`/viewed`(加法,2026-10-13 #941)**:App 进讲解页报一次。请求体 `{"from": recognition|search|collection|history|home|link}`(讲解页入口,取值外 → 422),Bearer 可选(带了就记到人)。**不挂在 `/content` 上**:生成中前端每 4s 轮询 `/content`,挂在那里会重复计数。恒 204,失败不影响页面。

**音频流式端点(加法,老 `/audio` 不动)**:`/audio/stream` 仅 guide/深度段(qa 连念/artist_bio v1 仍走 `/audio`)。⚠️ **同一个 200 有两种形状**——首播返 `audio/mpeg` chunked 字节流(单次 TTS tee:客户端边收边播 + detached 落库,断连也把整段落 R2,不重复付费);已落库返 JSON `{"audio_url"}` R2 直链。**前端必须按 Content-Type 分支**;409=同段他人正在生成(重试即缓存命中),404=该段文本未发布。流式响应无 Content-Length/不支持 Range。

`language` 取值 = `DEFAULT_LANGUAGES`(`lang_config.py`,唯一真相源;**本文不复制其内容**——曾硬列举成固定语言数并滞留数月,已改为纯引用)。缺省 `zh`。**加语言=加配置**:新语言按§多语显示名的"加语言 checklist"落配置即全端点生效,**本行不再随之改动**(引用真相源,非硬列举)。新内容全语生成;老内容缺语走懒翻译/`translate` 补。

## 1. `GET /museums`

馆列表,不含藏品。无 language 参数。

```json
[
  {"slug": "orsay", "name_zh": "奥赛博物馆", "name_en": "Musée d'Orsay",
   "city_zh": "巴黎", "city_en": "Paris", "country": "FR", "artwork_count": 262,
   "cover_image": "<url|null>"}
]
```

- `city_i18n`(加法,2026-09-29):十语城市名(`museums.yaml` `city_names` + city_zh/en),缺语言回退 `city_en`。
- `coordinates`(加法,2026-09-29):`[lat, lng] | null`,取自 Wikidata P625 配在 yaml。首页「附近」**在手机本地**
  按它算距离 —— **用户位置不上传**,后端只下发馆坐标(纪律 42)。
- 只列**已放出**的馆;`can_preview` 调用者另含隐身馆(可见性闸)。响应因调用者身份而异 → 前端缓存必须以身份为键(纪律 38)。
- `cover_image`(✅2026-07-20 spec museum-cover-intro-quality,加法):探索页列表缩略图(thumb 档),
  同 `m.cover_image_key` 一行零成本可读;未生成封面则 `null`(前端隐藏)。

## 2. `GET /museums/{slug}?language=zh`

完整馆包:馆元数据 + **分类 facet** + 按热度降序的全藏品。`language` 仅影响 `categories[].label`。

```json
{
  "slug": "orsay", "name_zh": "奥赛博物馆", "name_en": "Musée d'Orsay",
  "city_zh": "巴黎", "city_en": "Paris", "country": "FR",
  "qid": "Q23402", "source": "...", "generated_at": "2026-...Z",
  "artwork_count": 262,
  "categories": [
    {"code": "all", "label": "全部", "count": 262},
    {"code": "painting", "label": "绘画", "count": 259},
    {"code": "unknown", "label": "其他", "count": 3}
  ],
  "description": "奥赛坐落在一座1900年的火车站里…(AI接地叙事,按language)",
  "cover_image": "<url|null>",
  "artworks": [
    {"qid": "Q334138", "title_zh": "世界的起源", "title_en": "L'Origine du monde",
     "artist_zh": "居斯塔夫·库尔贝", "artist_en": "Gustave Courbet",
     "year": "1866", "period_zh": null, "period_en": null,
     "image": "<url>", "popularity": 51}
  ]
}
```

- `description`(✅2026-07-18 spec museum-intro,加法):馆叙事介绍,AI 接地生成 `description_i18n[language]`,缺→en→任一→**null**;2-3 短段落以 `\n\n` 分隔(2026-07-20 优化,不再是单一长段)。`cover_image`:封面 R2 直链(large 档,**可 null**)——**优先馆自身建筑外观照**(Museum.qid 的 Wikidata P18,不过安全闸:架构零裸体风险),无建筑照/下载失败则回落藏品图逐件得体性判定(古典/宗教裸体可,写实露骨否决)。前端 `as String?`,null 整块隐藏。老 App 不读不炸。

- `pass`(加法,2026-09-29):这家馆**在售**的通票 `{product_id, days, label, covers}`,`label` 按 `language` 本地化
  (范围名,如「巴黎」「荷兰」——前端不知道也不许假设它是城市还是国家),`covers` = 该票覆盖的**已放出**馆名;
  无在售票 → `null`(前端显示「暂未开售」,**绝不回落到某张默认的票**)。402 的 `detail.pass` 同形。
- `city_i18n`(加法,2026-09-29):同端点 1。
- `categories`:`all` 合计 + 各 `MuseumObject.category` 分组计数,标签本地化(`_CATEGORY_LABELS`:painting/sculpture/photography/decorative_arts/unknown)。
- `artworks[].title_zh` 永不为 null(回退 `title_en`→`qid`,防前端裸 `as String` 崩)。
- ⚠️ `artworks` 是**全量**(无分页);列表页改用端点 3。本端点保留供馆详情/概览。

## 3. `GET /museums/{slug}/objects`

分页藏品列表(列表页 A2/A3:分类 tab + 无限滚动)。

**Query**:`category`(可选,`all` 或省略=不过滤)、`sort`(默认 `popularity`)、`limit`(默认 50)、`offset`(默认 0)、`language`(默认 `zh`)。

```json
{
  "items": [
    {"qid": "Q334138", "title": "世界的起源", "artist": "居斯塔夫·库尔贝",
     "year": "1866", "thumbnail": "<url>", "content_status": "ready"}
  ],
  "total": 262, "limit": 50, "offset": 0
}
```

- `title` 按多语显示名规则:`title_i18n[lang]`(Wikidata权威)→ 该语言 legacy 列 → en 兜底。`artist` 同理经 name_i18n。
- `content_status`:**按请求语言解读**(2026-07-03 定)——对象有内容但该语言无已发布内容 → 返 `empty`(前端显"待完善",防"列表看着有、点进去空")。见末节生命周期。
- 未知馆 → 404。

## 4. `GET /museums/{slug}/objects/{qid}/content?language=zh`

单件讲解(导览页)。按 `language` 返对应语种已发布内容。

```json
{
  "qid": "Q334138", "category": "painting", "language": "zh",
  "status": "ready",
  "title": "世界的起源",
  "default_guide": {"body": "想象一下,站在一幅大胆的画作前…(单主线~300-600字现场导览)", "has_audio": true},
  "images": [{"url": "<url>", "credit": "..."}],
  "facts": {
    "artist": "居斯塔夫·库尔贝", "date": "1866",
    "medium": "...", "dimensions": "...", "inventory": "RF 1995 10",
    "location": "奥赛博物馆", "provenance": "...", "artist_life": null,
    "exhibitions": ["1988, New York...", "..."], "bibliography": ["..."]
  },
  "tabs": [
    {"section_code": "background", "label": "创作背景", "icon": "...",
     "body": "1866 年…(只写材料明说的;没有就不发布这一段)", "audio_url": null}
  ],
  "suggested_questions": [{"question": "...", "answer": "..."}]
}
```

- `default_guide`:**默认标准讲解**(单主线·5拍·~300-600字现场导览,识别后首先呈现的"主角")。`{body, has_audio}`,无则 `null`(前端回退 tabs)。⚠️ **是 `has_audio` 布尔值,不是直链**——列表接口只告诉你"有没有",真链要播时再调 `/audio` 端点(那里才走缓存/懒生成/付费墙)。(2026-08 更正:此处曾写作 `audio_url`,与实现不符,排查音频灌入时被误判为"灌入失败"。)**不混入 tabs**。前端分层页:default_guide 置顶 → 推荐 2-3 个 suggested_questions → tabs/其余收进"更多内容"。
- `share`(加法字段,2026-09-29):`{url, text, image_url}` 或 `null`。null = 这件在**请求语言**下不可分享
  (该语言无已发布 guide 正文 / 所在馆未放出 —— **预览账号也是 null** / 无自存主图),App 据此不显示分享键。
  `url` 落在公开网页 `/a/{slug}/{qid}`(只有文字,**没有任何音频**),`image_url` 是服务端合成的分享图。
  判定唯一真相源 `app/services/share.py`,网页 / 分享图 / 本字段共用。
- `tabs`:按类目的段落清单(`SECTIONS_BY_CATEGORY`)逐段(降级为"更多内容"深度模块;**overview 已退役**——默认讲解取代其作开场;**artist 已移出 tabs**——成独立作者卡;各模块各守互斥 lane、**不复述头条**、只会重复则返空不发布);`body` 为该语种已发布正文(无则 `null`);`audio_url` 为 R2 音频直链(未生成则 `null`,TTS 阶段)。
- `artist`:**必选常驻作者卡**(不随空隐)。**数据来自 `artists` 一等实体**(按 artist QID 生成一次、同作者所有作品复用→一致/完整/省;artist 不再是 per-work 段)。`{name, birth, death, nationality, notable_works:[...], bio}`(**name/title 按多语显示名规则解析:i18n 权威→翻译→en**;bio 按语言取)——生卒年/国籍/代表作取自作者 Wikidata 实体(P569/P570/P27/P800);`bio`=artist 段已发布叙事(无则 null)。~~v1 局限~~ ✅2026-07-04 解除:`nationality`/`notable_works` 按 language 本地化(`nationality_i18n`/`notable_works_i18n`:P27/P800 多语权威标签→translate_name 兜底→en 列;生成与 names 回填两路都填,幂等)。
- `facts`:**已策展+人性化的墙签事实**(只 wall_label 级):`artist/date/medium/dimensions/inventory/location`。`medium` 优先证据包干净源(Wikidata P186,多值合并人性化),回退 Joconde `medium_fr`;`dimensions` 取 Joconde 串人性化(证据包暂不抓 P2048/P2049,非法国馆无 Joconde 时为 null)。⚠️ **`provenance` 返 null、`exhibitions`/`bibliography` 返 `[]`——已移出面板**(学术噪音;参考文献彻底不展示,收藏/展览史进证据包材料级,阶段2 由 background lane 讲成流转故事)。`artist_life` 暂 null。
- `suggested_questions`:好奇心问答(0-4 条)。
- 对象不属于该 slug / 不存在 → 404。

## `content_status` 生命周期

`stub`(只元数据,目录铺出) → `ready`(≥1 段已发布)/ `empty`(无可接地材料)。前端:`stub`/`empty` 显"待完善",`ready` 正常。未知值按 `ready` 容错。

**懒生成(✅2026-07-03 落地)**:content 端点命中 `stub` → 后台触发该件完整生成(全语言;**请求者语言排队首、逐语言翻完即落库**——用户最快看到自己的语言,单语言翻译失败不拖垮其他),几分钟后再取即 `ready`。

**首屏关键路径原则(✅2026-07-16 #257 定,TTFC 45.9s→~15s)**:懒生成语句顺序=**请求者首屏最短路径**——材料抓取(guide 的接地输入:对象/作者 wiki 提取 + artist_facts + 证据包,**必须在 guide 前**)→ guide(en) 落库 → **请求语言 guide 翻译立即落库(用户 ~15s 见主讲解)** → 其余全部延后(作者实体 bio/i18n、canonical 深度段、其余语言、QA)。**今后往管线加任何生成步骤,先问:在 guide 依赖链内吗?不在 → 一律放首屏之后**。纯重排:调用集/prompt 不变=质量与成本不变;每段 persist 即 commit=前端轮询立即可见。锁=内部 `attributes.lazy_lock_at`(TTL 10min 自愈),**不对外暴露中间状态**——stub 期间前端照旧"待完善",契约形状零变化、老 App 无感。`empty` 不重试(已判无可接地材料,防循环烧钱)。并发上限 2/进程;仅 staging/production 环境生效。

**首屏关键路径原则·补记(2026-10-10,#882/#885)**:① guide 前的联网取数(作品资料 / 看图 / 多语标题 / 作者解析→作者资料与事实 / 证据包富属性)**互不依赖,必须并发发出**,首屏 = 最慢那一路而不是各路之和;DB 会话不进线程,结果回主线程**按原顺序**落库(写入面不变);被多路共用的限速器必须线程安全。② **提速边界(用户 10-10 定)**:首屏优化**不许以落库内容变薄为代价** —— 内容生成一次永久落库,"可选材料超时就不等"省下几秒,换来的是这件作品**永远**少一块材料。所以只做并发、换更快的接口(纪律 44)、跳过已有的数据,**不设"超时即放弃"**。实测:准备阶段 17–31s → 5–8s(瓶颈变成看图 4–6s),中文讲解可见 27–42s(偶发 70s)→ 15–18s(prod 17.3s)。

**`generation` 进度字段(✅2026-07-10 加法)**:content 端点返回 `generation: {published, expected}`——真实段落分数(expected=guide+该类目深度段;published=已发布的 guide+深度段)。前端显"N/M 段"诚实进度(**不做假百分比/时间进度条**:LLM 时间不可预测,假条会卡在90%伤信任)。配合 guide 先出流式,等待体验=主讲解先出+真实段落进度+计时预期。

**`generating` 字段(✅2026-07-04 加法)**:content 端点返回 `generating: bool`(信号源=懒任务锁)——true=懒生成/懒翻译进行中。前端三态:generating→"生成中"继续轮询;false+empty→"资料不足"停;false+stub 无内容→"待完善"+重试入口。老 App 不读则无感。

**`unavailable_reason` 字段(✅2026-10-10 加法,#877)**:content 端点在**带身份的请求**里说明"为什么没讲解、也没在生成":`"daily_cap"` = 当天懒生成名额已满(全局按 UTC 日计,只数懒生成/懒翻译写的段,上限 1000 段 ≈ 120 件;运营批量生成不占;**另有每账号 160 段 / 每 IP 300 段的日额度**,点火时按估算段数扣:懒生成 8、懒翻译 3,Redis 计数、Redis 不可用时放行,`can_preview` 账号豁免,超了同样返回 `daily_cap`,2026-10-11 方案 A),前端提示"今天的新讲解名额已满,明天再来"、**不给重试入口**(重试必然再失败);`"no_image"`(2026-10-11 方案 B)= 无图 stub 不生成讲解,**带身份与匿名请求都给**,前端显示「暂无讲解」不给重试(老 App 不认 → 仍显示重试,但列表/搜索/识别/分享都到不了无图 stub);`null`/缺省 = 其它情况,沿用 `generating` 三态。匿名读不点燃生成。老 App 不读则照旧显示"待完善"+重试。前端解析 `as String?`。

**懒翻译(✅2026-07-03 落地,懒生成姐妹场景)**:content 端点命中"对象 `ready`、有 en 轴心、但**请求语言**无已发布内容" → 后台**只翻这一门语言**(补语种原语:段落+问答+作者bio,数十秒、费用分钱级)。配合**列表 content_status 按请求语言解读**:该语言缺 → 列表即显"待完善",点开触发懒翻译,刷新即有——任何语言视图所见即所得,新加语言自动享受同样行为。同锁/并发/环境门。

## 图片字段（✅2026-07-03 R2 自存落地）

`image`(端点2)/`thumbnail`(端点3)→ **thumb 档**(480px);`images[].url`(端点4)→ **large 档**(1600px,兼识别参照)。`ObjectImage.image_key` 存**基础键**(`images/{qid}/{sort}`),端点拼 `_thumb.jpg`/`_large.jpg` 出 R2 直链;无 key 回退 `source_url`(Wikimedia)。字段名不变,前端零改。

- **多角度图**:catalog 收 P18 全部值 → 多行 ObjectImage(首张 `role=primary`,其余 `view`;雕塑识别参照)。Commons 分类(P373)深挖留给识别机制 brainstorm。
- **物化**:`onboard.py <slug> images --target <env> [--limit N]`——下载(合规UA限速)→Pillow两档(JPEG q82,不放大)→R2→Commons 署名(license/credit,CC-BY 摄影必署)。逐行幂等,失败留空重跑重试;SVG/超60MB 跳过。不存原图(source_url 可重下)。
- **懒补漏**:content 端点发现该件缺图 → 后台补单件(自愈运维疏漏/新进目录;不占内容锁)。
- **⚠️ 成本分界(通用原则)**:**图=目录门面必须预物化**(列表一屏几十张缩略图多数永不被点开;识别参照库必须先于识别存在;成本≈0)——与**内容=必须懒生成**($/件)相反。新馆照此:catalog→names→images 全量预跑,generate 分层。
- **图源授权判据(2026-10-05 S7 补图定,通用规则)**:**只用"这一张图"有明确授权证据的图**,证据按来源:
  ① Wikidata P18(Commons 文件,署名由物化器从 Commons 抓);② Wikidata **P4765「Commons 兼容图像 URL」且带限定符 P275**(如 CC0 = Q6938433;
  无 P275 的不算,卢浮宫 3744 件 P4765 指向官网下载链接即属此类);③ **馆方作品页对这张图的逐图授权标注**(如 Paris Musées
  `image-centrale` 首图 `span.droits` 以 `CC0` 开头)。**不用**:网站条款禁止商用的(卢浮宫/奥赛官网图须向 RMN-GP 付费申请 ——

  只写机构名不写授权的(`Paris Musées / …` 无 CC0);© 摄影师/图库。抓馆方页面遵守 robots `Crawl-delay`;官方 API 需注册时先评估公开页能否替代。

## 收录策略（通用规则,任何馆 0 代码复制;2026-07-03 定）

**① 分层收录(2026-07-13 取代"有图才收录"硬规则;版权边界语义不变)。** 三层：
**视觉可识别层**(有自由版权图 P18/Wikimedia——图仍是识别参照物+合规边界,官方 RMN 类版权图照旧不碰)→向量识别+列表展示全功能；**文字可识别层**(有 Wikidata 条目无图,catalog P18 已 OPTIONAL 收全条目)→墙签 OCR/馆藏号/搜索命中,讲解懒生成照常,**列表与分类计数不出现**(浏览面密度优先),馆页双数字揭示规模;**需求层**(无条目)→unrecognized+记需求。无图件讲解页 hero=识别路径用用户自己照片(会话内回显)/搜索路径类目占位图。

**② 三层口径与北极星 KPI(2026-07-13 验收换轴)。** 口径:官方全馆藏(奥赛~15万) ≫ **常设在展(3-4千,真实分母)** > Wikidata 条目(5353=档案层) > 有图(~2065=图录层)。**上新馆验收不看导入件数,看"现场识别成功率"**——用户实拍一件眼前藏品被正确识别的概率(recognition_events 聚合:(match+确认候选)/尝试)。**KPI 归因口径(2026-07-13 实测修正)**:App 主入口是全局识别端点(事件 museum_slug 为空),按**命中对象的归属馆**归因;全局且未命中(top_qid 也空)的事件无法归馆、不计入任何馆的分子分母(诚实局限,不引入方向性偏差)。`onboard coverage-report`(配方 6b 步,在 `verify` 之前)输出分层数字/展陈分布/KPI 并回写 museums.stats(馆页双数字数据源)。

   类别词要**整词**匹配 —— 子串会让 `(Kölner Meister)` 撞上 `öl`、`(boiler)` 撞上 `oil`。

   ⚠️ **zh-hant 的兜底源顺序是个语言学判断,不是随手排的**:链为
   `zh-hant → zh-tw → zh → zh-hans → zh-cn → zh-hk`。**zh-hk 必须排在 zh 之后** ——
   港式音译是粤语拼读的另一套传统(Cézanne→施傘 / Giorgione→佐助彌 / Christoffer→基斯杜化),
   排在 `zh` 前面等于"宁可要另一个传统的音译,也不要本传统的简体转繁"。
   实测 Q35548 无 zh-hant/zh-tw 标签时,旧序取到「保羅·**施傘**」并被当 glossary
   注入每一段繁体译文,逐段复制污染 27 段正文。

   ⚠️ **上游权威源本身可能是错的**,不能因为它是"规范名"就免检:
   `Q5592` Michelangelo 的 **fr 标签**就是 `Michel-Ange Buronarroti`(Buonarroti 拼错);
   `Q1923320` 的 es/it/pl 标签仍是卢浮宫 2019 年已弃用的冒犯性旧称
   (`Portret Murzynki`),而 en/fr 早已改成 `Portrait de Madeleine`。
   → 上新馆后至少做一次形式普查(编号/年份/括号/引号配对/非拉丁语位无本族文字),
   **这类缺陷用户不会专门反馈,但会一直长**(第 24 条)。
4. **物化图片**:`python scripts/onboard.py <slug> images --target <env>`(物化完自动给宽幅作品切识别块,见§识别)
   → 全馆缺图行下载→两档→R2→署名→**入库即嵌入**(幂等;见§图片字段。存量老库用 `backfill_embeddings.py` 补漏,新馆此步已自动嵌入,无需额外跑)。
   - **4a 雕塑/立体作品多视角**:`onboard.py views --museum <slug>` 插 Commons 他人照片行 → **再跑一次 `images`** 物化。
     view 与正面照的相似度闸在物化嵌入时自动执行(删/隔离/入索引,见§识别);`vet_view_images.py` 只用于存量或换引擎后重标,新馆不用跑。
   - **4b(可选)必看/易认错的画作补他人实拍**:`onboard.py recog-views --qids Q1,Q2,…` 后**只对这批件**物化
     (无现成命令:按件调 `materializer.materialize_object_images`,写法参考 `scripts/add_works_by_qid.py`),不跑整馆 `images`(它会顺带整馆切块,纪律 37 补记)。只进识别索引。
   - **4c(可选,法国馆)展陈证据**:`onboard.py display-evidence --museum <slug>`(Joconde P347 → 展陈位置)。
5. **生成内容(可选)**:`python scripts/onboard.py <slug> generate --target <env> [--qid Q..|--limit N] [--langs zh,en,fr]`
   默认不批量预生成,靠懒生成按需兜底(§收录策略⑤);运营定了 top-N 再跑。
   → 逐件:stub 抓材料(Wikipedia/Joconde)→ 生成 → 接地闸 → 翻译 → 落库 → `ready`/`empty`。
6. **馆介绍+封面**:`python scripts/onboard.py <slug> intro --target <env>`(见§博物馆介绍)
   → 接地生成馆叙事简介(按语言补缺)+ 选封面。**封面零额外配置**:优先取步骤①已填的
   `wikidata_qid` 的 Wikidata P18(馆建筑外观照,自动下载物化);无 P18 才回落藏品图逐件
   得体性判定。**这是"零代码上新馆"最新的一条自动收益**——不用为封面单独准备图源。
   **6b. 覆盖率报告**:`python scripts/onboard.py coverage-report --museum <slug>` → 分层数字/展陈分布/KPI,
   回写 `museums.stats`(馆页数字数据源)。
7. **验收闸(最后一步,全绿才算上完)**:`python scripts/onboard.py <slug> verify --target <env>`
   → 把卢浮宫暴露的**六类事故固化成自动检查**:各语言译名覆盖 ≥95% / 英文标题空值 <1% /
   作者中文名 ≥90% / `artist_qid` 格式合法(挡 blank node 假身份)/ 图物化无残留 /
   介绍已分段 + 封面已选。**每项红了直接给补救命令**;非零退出可串进上馆脚本当闸。
   ⚠️ 契约里的教训是文字、会被跳过,**这个是跑得起来的**——上新馆最后一步必跑。
   「门面响应 <1s」这项先热身再计时(#693),冷启动不会假红;小皇宫热调用 931ms,
   离阈值只剩 69ms —— 上更大的馆时这项可能真红,那时按提示去查有没有全量加载混进门面路径。
8. 端点自动产出上述五个契约;前端零改接入。

> **✅ 上新馆默认隐身(可见性闸,2026-09-29 上 prod;spec `2026-09-20-museum-visibility-gate`)**:
> 馆由 `catalog` 插入时 `museums.published_at = NULL` —— **普通用户看不见,只有 `users.can_preview` 账号可见**
> (馆列表/馆包/藏品/讲解/音频/搜索/识别/解锁全部过闸;隐身与"不存在"返回**同一个 404**,不是 403)。

> 放出前 `verify` 必须全绿,含第 ⑧ 项「被在售通票覆盖」(否则用户看得到内容、撞墙、买不了票)。

**非 Wikidata 主源的馆**(如美国 Met):一次性写个 `CatalogSource` 连接器(同插件模式,核心零改),其余同上。

`--target` 必须匹配容器 `ENVIRONMENT`(守卫防误灌)。全量富化在 prod 跑(staging 仅样本验证机制)。

> **⚠️ 批处理纪律(2026-07-03 定,prod 三次崩溃换来;适用于全部上馆命令 catalog/names/images/translate/generate 及未来新批任务):**
> 1. **单件/单批失败跳过继续**——错误计数(`errors`)不炸全局(教训:一次 Wikidata ReadTimeout 炸死整馆 names);
> 2. **分批落盘**——每 N 件 commit(names 50/images 25),崩溃/重部署不丢进度(教训:253 件进度全丢);
> 3. **批量外部查询必须分批 + 瞬时错误重试**——VALUES 有 URL 上限(教训:1300 QID 单条查询 HTTP 414);5xx 重试一次仍败跳批(教训:Wikidata 502);
> 4. **一切批任务幂等可重跑**——重跑只补缺,断点即续传。新写批任务时按此四条自查。
> 5. **空响应≠数据到底,必须重试后再判**(2026-07-11 添)——WDQS 深 OFFSET+ORDER BY 超时会返回
>    HTTP 200 的**空结果**,把空页当"翻完了"会**静默缺件**(教训:orsay catalog 两次截断 1537/1517,
>    漏收 500+ 长尾件含用户实拍的库尔贝《鹿斗》)。翻页循环连续空 N 次才允许 break;
>    上新馆跑完 catalog 核对 loaded 数与该馆 Wikidata 有图量级是否相符。
> 6. **容器内长任务:避开部署窗口 + 脱会话 + 日志必须实时落地**(2026-07-16 添)——后端容器随每次
>    staging/prod 部署 **recreate,里面的批任务被无声杀死**;起长任务前确认无部署在途/等部署落定再起。
>    启动用 `docker exec -d` + `setsid`(SSH 断连不死);日志逐行 flush 到文件(教训:staging Joconde
>    补名首跑中途死、日志 0 字节,**死因无法回溯**;重建带日志脚本后 1038 件零失败跑完)。
>    "监控到进程消失"≠"任务成功"——收尾判断只认日志 DONE 行 + 数据核验(纪律 4 幂等保证随时续跑)。
> 7. **外部服务硬上限 + 外部自由文本必须按列宽截断**(2026-07-25 卢浮宫 17k 件添,三个坑
>    **全是 staging 小样测不出、只有规模才现形的**)——上更大馆(大英/Met)前按此自查:
>    - **OpenAI Batch 单 job 上限 5 万请求**(硬限,超了提交即 `maximum_requests_exceeded`,
>      不是软限流)。件数×语种很容易破:17283×多语 ≫ 5 万 → `batch_names.run` 切 ≤50k 块,
>      **先全部提交**(OpenAI 侧并行跑,别串行等)再逐块收,`job_id` 存逗号分隔多 id 供续传。
>      staging 只 810 任务故从未暴露。
>    - **Commons 署名(credit)是自由文本,可长达数百字**(多段落说明+英法双语+联系方式),
>      超 `varchar(255)` 直接 `StringDataRightTruncation` **崩掉整轮物化**(实测 1369/10159 处崩)。
>      入库前一律按列宽截断(`_clip`),截断不影响合规归属。**凡外部来源的自由文本字段,
>      落库前都要问一句"最长能多长"**。
>    - **WDQS 深翻页(~18k 件)高频瞬时 502/ReadTimeout**,且 catalog 落库全有或全无、
>      一崩整批丢 → `run_sparql` 统一重试 4 次指数退避(5/10/20s)+ 超时 120s,两个 SPARQL
>      消费者共用。三次全量跑两次栽在这上面才补的。
> 8. **规模会让"本来没问题"的设计失效——上新馆后必须实测端点耗时**(2026-07-26 卢浮宫添)。
>    以下三条**都不是写错了,是量变引起质变**:奥赛 6.8k 件时全都正常,卢浮宫 17k 件全崩。
>    **所以判断性能不能靠读代码,必须在真实数据上测**(`curl -w "%{time_total}s %{size_download}"`)。
>    - **"全量返回"会从可用变不可用**:馆包把全部藏品塞一个响应,奥赛 1.8MB(勉强)→
>      卢浮宫 **5.0MB / 8.2s**(手机上几十秒)。更荒唐的是前端 `MuseumDetail` **根本不解析
>      `artworks`**——下载完就扔。→ 加 `artworks=false`(加法参数,缺省 true 保老 App),
>      **门面只返回 cover/categories/description,列表走分页 `/objects`**。实测 8.2s/5.0MB →
>      **0.06s/1.9KB**。**新增任何列表型响应先问:调用方真的要这些数据吗?**
>    - **进程内缓存的冷建成本随数据量涨**:搜索索引 6.8k 条目 ~2s(可忍)→ 24k 条目 **7.2s**。
>      TTL 600s × 2 worker = **每 10 分钟每 worker 坑一个用户等 7 秒**。→ **stale-while-revalidate**
>      (过期先返旧索引、后台重建)+ **启动预热**;重建失败保留旧索引(搜不到新件好过 5xx)。
>      **凡"过期后同步重建"的缓存,数据量一涨就是定时炸弹。**
>    - **每件一次的外部调用(N+1)小馆看不出、大馆致命**:names 取权威标签每件一次 SPARQL,
>      17283 件 = 17283 次串行往返(**5 小时**,CPU 仅占 12%,全在等网络);10 万件馆 ~30 小时
>      直接上不去。→ 批量化(VALUES 200/批),**5 小时 → 5 分钟**。**判据:CPU 占比远低于
>      墙钟时间 = I/O 阻塞,先查有没有 N+1。**
> 11. **小馆的 `popularity` 排序会失真,`--limit N` 选不出招牌**(2026-07-27 橘园添)。
>    `popularity` 取自 Wikidata sitelinks,对大馆有效(蒙娜丽莎 146),但**小馆/系列作品会塌**:
>    橘园**睡莲六联作 popularity 全是 0**,而《保罗·纪尧姆肖像》是 6 —— 按热度取前 N 预热,
>    **招牌反而排在最后**。原因:同一作品拆成多条目,每条的 sitelink 都很少。
>    **对策**:小馆预热/排序**按"有图"筛选或显式列 qid**,别依赖 `--limit N`;
>    ("有图"=可拍照识别=用户魔法时刻的入口,比热度更贴近真实价值)。
>
> ⬇️ 原纪律 **⑨⑩⑫⑬** 与博物馆无关(shell 编排 / 判进程 / 不可逆批量操作 / 替换过闸),
> 已移到下一节 [§工程与运维纪律](#工程与运维纪律与馆无关适用于任何批任务)。

## 工程与运维纪律（与馆无关,适用于任何批任务）

上一节那些纪律都是**跑上馆管线**才会踩的;这一节与博物馆、与语言都没关系 ——
凡是写批任务、跑容器内长任务、做不可逆的批量替换/删除,都适用。
⚠️ **本节开节时(2026-07-29)只有四条(⑨⑩⑫⑬),此后持续增长(编号已到 53),
「上第二个馆的人可以跳过本节」已不成立** —— 第 15(只给已发布内容做下游产物)、
第 28(挂起≠缺口)两条与内容质量直接相关,上馆验收(配方第 7 步 `verify`)会直接踩到。

> ⚠️ **编号沿用原「批处理纪律」序号(⑨⑩⑫⑬),搬家不改号。**
> `material.py` / `batch_names.py` 的代码注释、plans/specs 都按号引用(如"纪律①""纪律⑥"),
> 重排编号会让这些引用全部指错地方。

> 9. **多步批任务:用 `&&` 不用 `;`;完成标记只在真成功时出现**(2026-07-27 预热添)。
>    `;` 连接的命令链,中间崩了后面照跑、末尾照打 "ALL_DONE" —— **"打印了完成标记"≠"全部成功"**。
>    实测教训:三馆预热六条命令用 `;` 串起来,Joconde 崩掉 orsay/orangerie 两步,链条仍打印
>    `PREHEAT_ALL_DONE`;**第二次加了分步标记 `STEP_*`,用的还是 `;`,同样无效**——同一个坑踩两次。
>    两次都是靠**核验数据**(件数没涨)才发现的。改用 `A && echo OK_A && B && echo OK_B` 后,
>    标记才真正等价于成功。**收尾一律:看标记 + 核验数据,两者都对才算完(纪律⑥的加强版)。**
> 10. **判进程要认执行体,不认编排它的外壳**(2026-07-27 添)。用 `/proc` 或 `docker top` 按
>    命令行子串判断"任务还在跑"时,`sh -c "A && B && C"` 外壳的 cmdline **包含整条链的字符串**,
>    A 的进程早退出了外壳仍匹配 → 误判"还在跑"。实测后果:自动切换逻辑没触发,本该被拦截的
>    橘园全量任务跑了 7 件。判定要求进程名以 `python` 开头(或比对 PID),别只匹配子串。
>    ⚠️ 附:**后端容器里没有 `ps` / `pgrep` / `pkill`** —— 判活用宿主 `docker top`,
>    容器内定位/终止用 Python 读 `/proc` + `os.kill`。
> 12. **不可逆的批量操作:护栏比功能重要**(2026-07-29 R2 孤儿回收添)。删除/覆盖线上
>    资产的脚本,一次跑错就没有回头路,五条护栏一条都不能省:
>    - **默认 dry-run,必须显式 `--apply`**;
>    - **宽限期**(如 7 天):覆盖"客户端还拿着旧直链在播"与"刚写入未提交"的竞态;
>      ⚠️ **年龄不能只看存储侧的写入时间**(2026-10-13 #953):一年前录的音频昨天才被换下,
>      R2 写入时间是一年前、却可能正有人在播。按「存储写入时间」与「该位置在 DB 的 `updated_at`」
>      任一落在宽限期内就不删;
>    - ⭐ **引用集合为空则立即中止** —— 查询写错/连错库都会让它变空,照删就是清空整个库;
>    - **删除占比超阈值(如 50%)中止** —— 正常不该这么多,先去查对账逻辑;
>    - **先列存储再读 DB**:列举期间新写入的 key 必已在 DB,不会被误判成孤儿。
>
>    ⚠️ **引用集合必须覆盖"所有存过这个 key 的地方",漏一处就删掉正在用的文件**。
>    音频 key 存在**三处**:`object_content_sections`、`object_suggested_questions`、
>    **`artists.bio_audio`(`{lang: key}` 的 JSON,最容易漏)**。
>    prod 首次 dry-run:21 个孤儿 / 32.1 MB,全是历史改名遗留。
> 13. **替换已有内容必须过质量闸,不过闸就不替换、保留旧版本**(2026-07-29 自托管 TTS 添)。
>    替换是不可逆的(旧文件即刻成孤儿),而**模型回归会静默毁掉整个库**——不报错、
>    不变红,等用户投诉时已经全量替换完了。所以先验后替:空/截断/无限重复用字节级估算
>    就能抓住(**不引入 librosa/ffmpeg**,要在批量管线跑几万次);最有用的是
>    **替换偏差检查** —— 同一段文本换引擎,时长差一倍必有问题。同理适用于换生成模型、
>    换翻译引擎:凡"用新产物覆盖已上线产物"的批量操作,都要有一道能拦住回归的闸。
> 14. **文本比对做校验前必须先归一化,否则对特定语言系统性误判**(2026-08 橘园音频试点添)。
>    用「转写 vs 原文相似度」校验音频内容是否读对时,**不归一化会把正确的判成错的**,
>    而且是**按语言成建制地误判**——实测两类:
>    - **变音符**:西语真实一致度 1.00 被算成 **0.53**,纯粹因为 `Tómate` vs `Tomate`;
>      de/it/fr/pl 同样受害。→ NFKD 分解后去掉 combining 字符。
>    - **简繁**:转写引擎常把繁体音频写成简体字,码位全不同 → 实测 **0.50**,归一化后 **0.90**。
>      → 比对前统一转一种字形(OpenCC `t2s`)。
>    后果不只是"报错":管线会**重试 3 次再判失败**,等于三倍算力换一个错误结论。
>    **通用推论**:任何跨书写系统/带变音符语言的自动校验(音频、翻译回译、OCR 核对),
>    都要先问"我的相似度函数对这个语言公平吗",别把归一化缺陷当成质量问题去调模型。
> 15. **只给「已发布」的内容做下游产物**(2026-08 橘园音频试点添)。
>    队列若不过滤发布状态,会把 `needs_review` 的内容也排进去,而前端 `/content` 只返回
>    published —— 生成侧取不回正文(白跑+重试),灌入侧质量闸同样取不到文本(判失败)。
>    实测橘园 de+it 116 段里 9 段是 needs_review(**7.8%**),按此比例外推全量约
>    2300-2600 段无效任务。**凡"为内容生成衍生产物"的队列(音频/翻译/嵌入/缩略图),
>    都要以发布状态为准入门槛。**
>
>    ⚠️ **但"过滤掉"不等于"处理掉"** —— 这是同一枚硬币的另一面。`needs_review` 意味着
>    **该语言的用户打开这件作品连正文都看不到**(前端只返回 published),音频缺失只是连带的。
>    过滤只省下了算力,内容缺口原样还在,而且**在"生成 28/30 条成功"这类报表里是隐形的**。
>    实测橘园 `Red-Haired Girl` 的 de/it 被挂起,各是一个真实形式缺陷:德语把

>    报"成功 N 条"时必须同时报"缺口 M 条",否则缺口会被成功数掩盖。

>    **prod 实测基准(2026-08-31,可作新馆的预期值)**:全库 needs_review **1471 段/6.8%**,
>    涉及 **602 件**作品(613 件有内容的作品里几乎每件都至少缺一段)。
>    分馆:louvre 6.5% / orsay 7.1% / orangerie 7.8% / petit_palais 16.7%。

>    🔴 **订正(2026-09-01):`needs_review` 是两类东西,上面那句「意味着内容缺口」

> 16. **「首次写入」和「替换已有」是两条路,必须各自被真跑过**(2026-08-31 橘园重灌添)。
>    首次写入时 `old_key` 为空,会**整段跳过**替换分支(取旧对象大小、算偏差)。
>    上新馆永远走首次路径,于是替换路径可以潜伏很久 —— 实测第一次真替换就炸:
>    `storage.size()` 返回字节数(int),调用方却拿去 `len()`,`TypeError`。
>    更值得记的是**测试为什么没挡住**:
>    - 旧测试写成 `f(n if isinstance(n, bytes) else audio_bytes)` —— isinstance 恒为假,
>      **永远在测 bytes 路径**,恰好绕开了它声称要测的 int 路径。
>    - 新加的测试里,存储替身 `size()` 返回 `None` —— 于是替换分支同样整段被跳过。
>
>    **推论**:① 凡有「首次/更新」二分的写入路径,两条都要有测试真正执行到;
>    ② **测试替身的返回类型必须与真实实现一致**(真实返回 int 就别返回 None),
>    否则测的是一条现实中不存在的路径;③ 测试里的条件分支若绕开被测路径,测试就是假的。
>    验证办法很简单:**把修复撤掉,看测试会不会红** —— 不红就是假测试。
>
>    **第三例(2026-09-01 橘园第二批,同一形状换了个身位)**:生成侧取文本时,
>    `guide` 走 `default_guide` 分支、深度段走 `tabs` 分支。第一批只做 guide,
>    于是 `tabs` 那条分支**一次都没执行过** —— 里面把字段名写成了 `t.get("code")`
>    (实际是 `section_code`),恒为 None。后果比崩溃更坏:**它不报错**,
>    60 条深度段会被判「无文本,跳过」,状态里写 `no_text`,**看起来像内容缺失而不是 bug**。
>    → 分支不只由「首次/替换」二分,**也由输入取值二分**:小样本试点若只覆盖了一种取值,
>    另一种取值的代码就从没跑过。扩量前**先用全部取值各跑一条**(纯取数、不生成,
>    成本 1 分钟),这次正是它把 6 小时的空跑挡在了门外。
>    **补记(2026-10-10 #883,同一失效模式在生成侧)**:证据包只在「重生成」路径上进得了材料 ——
>    `generate_object` 先拼材料、后建证据包,首次生成(懒生成 + 上馆批量)时包还不存在,讲解/深度段/问答
>    一律没吃上 Wikidata 富属性;`--force` 重生成时包已在库,于是一直"能用"。§首屏关键路径原则早就写着
>    "证据包必须在 guide 前",测试只断言了"证据包落库了",没断言"首次生成的材料里有它"。prod 924 件已上线件中
>    152 件有材料里没有的具名事实(委托人/来源作品/影响等),正文用上的仅 3 件。
>    → 凡"材料组成部分"都要有一条**首次生成路径**的测试,断言"进了模型的输入",而不是"写进了库"。
> 17. **幂等要留「修复重灌」的出口**(2026-08-31 橘园重灌添)。
>    灌入按 `audio_engine` 幂等(已是目标引擎就跳过),这对防重复灌入是对的,
>    但会挡住一个真实场景:**引擎没变,坏的是产物** —— 生成侧修了 bug 要重灌。
>    没有出口时,人就会去改引擎标记或手工改库绕过,两者都更糟(前者在数据里撒谎、
>    把覆盖率报表劈成两半,后者不留代码痕迹、下次还得再来一遍)。
>    → 提供显式的 `--force`:**只跳过幂等,质量闸与偏差检查照常跑**。
>    **通用推论**:凡"按标记判完成"的幂等设计,都要同时回答"标记没变但产物要重做怎么办"。
> 18. **判定类工具必须先用已知正/负样本验证判断力;修好工具后必须重跑全量**(2026-08-31 添)。
>    失灵的检查比没有检查更糟:它一边烧算力(重试),一边把合格内容永久标成失败,

>    丢弃频率 >1% 的元素),把真值 0.9946 的转写打成 **0.5027**。

> 19. **质检的两端不能来自同一个被污染的源**(2026-08-31 添)。
>    音频质检拿"转写 vs 原文"算一致性 —— 但当原文自己带缺陷时,缺陷会**同时**
>    出现在两端,于是判"完全一致"直接放行。实测:4 条讲解正文开头被模型回贴了
>    语言标签(`Polish:` / `日本語:`),TTS 老实地把标签念了出来,一致性照样满分,
>    三道闸全过,灌进 prod 后用户在 App 里听到"日本語"开头。
>    → 校验只能证明"产物忠实于输入",**不能证明输入本身是对的**。
>    凡"拿输入当标准答案"的检查,都要另有一道**只看产物形态**的检查

> 20. **形式缺陷需要形式检查 —— 内容闸一概看不见它**(2026-08-31 添)。
>    译文回贴语言标签的问题波及**全库 1091 段**(pl 289 / it 267 / de 144 …),
>    而两道闸都放行:忠实度闸看事实(前缀不改变任何事实)、语言检测闸看语种
>    (正文确实是目标语言)。根因更值得记:**翻译 prompt 的输入格式在自我诱导** ——
>    user 消息写成 `English:\n{原文}`,模型照猫画虎输出 `Polish:\n{译文}`;
>    system 里那句 "Return ONLY the translated text" 拦不住,**格式示范比指令更强**。
>    → ① 给模型的输入别用「标签: 内容」的形态(改用 XML 标签包裹);
>    ② 落库前加一道形态剥离兜底;③ **剥离只认已知白名单,不做通用的"短词+冒号"**
>    —— prod 广谱扫描证实正文合法地以 `Oto ciekawostka:`「這裡有個有趣的小知識：」
>    这类短语开头,通用剥离会削掉正文的头,**误伤比漏网糟**。
>
>    **补记(2026-10-14):这是一类,不止格式标签 —— prompt 里一切具体样例都是示范,会被照抄。** 三个实例:
>    ① 本条的 `English:\n` 输入标签 → 输出 `Polish:`;
>    ② 翻译 prompt 注入规范名写成 `「{title}」`,直角引号被学成"引用作品名的写法",prod 3603 段 + 1118 条问答的
>      法/西/意/德/波/韩正文套上中日式标点(2026-09-14,`prompts.py` 注释);
>    ③ 作品意义段写作要求举例 "called the artist's masterpiece or one of their most famous works" →
>      30 件草稿 29 件开头「是 X 最著名的作品之一」,多数材料里没有(2026-10-14)。
>    → 写作要求只写**结构约束**(如「每句须复述材料里关于这件作品的原话」),不举「可以写什么」的具体措辞;
>      注入的值用 XML 标签包裹,不用会被当成标点的符号。
>    ⚠️ **禁用词清单不在此列**:同次实验去掉禁用词清单,发布句无出处反而 8→15 —— 禁令要留,
>      且按纪律 35 长在它约束的那一拍上。
> 21. **LLM 判定的批量翻案,必须带旧判据对照组;而且要读旧判据的原文,不能只看判决翻转**
>    (2026-08-31 添)。修好一个 LLM 闸的 prompt 之后重跑存量,一部分条目会**仅仅因为
>    模型的随机性**翻盘 —— 那不是修复的功劳。做法:每条用新旧两版 prompt 各判一次,
>    `旧✗新✓`=修复归因、`旧✓新✓`=闸自身噪声、`旧✗新✗`=真该卡。没有对照组就分不清
>    "修好了"和"掷骰子掷赢了",而后者会让你**凭运气往 prod 放内容**。
>    实测(539 段忠实度复检):fix 68.8% / noise 3.3% / real 27.3% —— 噪声只有 3%,
>    归因站得住;若噪声很高,那说明闸本身不可靠,是另一个要单独谈的问题,
>    绝不能混在批量里悄悄放行。
>
>    🔴 **只看判决翻转会漏掉最重要的东西。** 判决翻转只说"变了",不说"为什么变"。
>    这次的替代解释是:新 prompt 里那句 "must NOT be reported as an infidelity"
>    可能只是把检查器整体调宽松了(与标题无关)—— 若如此,72% 的"解锁"就是批量放行
>    坏译文。**验证办法是抽样重跑旧 prompt 并读它原本抱怨的文本**:60 条里约 50 条
>    抱怨的确实是标题,归因才成立。⚠️ 所以复检脚本**必须保留旧判据的理由字符串**,
>    只存布尔结论等于把证据扔了(本次就扔了,只能补跑一轮)。
>    呼应第 6 条:小样本推出的比例,必须保留分解到各环节的原始计数与理由。
>
>    🔴 **补充(2026-09-01):判据自己也要跟自己比一遍,而且批量写入取多遍的交集。**
>    `default_complete` 用 `temperature=0.3`,同一条输入两次判定结果可能不同。
>    实测 415 条问答重判:第一遍 208 条可发布、第二遍 211 条,**两遍不一致 15 条(3.6%)**。
>    单遍的数字看不出这一层。→ 批量翻案**跑两遍取交集**(本次 202 条),
>    偏保守的一侧:误发布比误扣住糟得多。抖动率本身也是信号 —— 3.6% 可接受,
>    若两位数则说明判据不堪批量使用,该先修判据而不是先翻案。
> 22. **管线注入给一侧的规范名,必须同样告诉另一侧 —— 这是一类,不是一个 bug**
>    (2026-08-31 添)。翻译侧会把规范**标题**、规范**作者名**(未来还有馆名)当
>    glossary 注入译文以消除分叉;忠实度检查侧只被告知了标题,不知道作者名,
>    于是把注入的作者名判成错译 —— 与标题那桩冤案**同构**,只是低一层。
>    → 修一个实例时,先问"同一个注入机制还喂了什么进去",把整类一起修;
>    只修被投诉的那个实例,剩下的会继续流血(实测:147 条判定为"真不忠实"的段里,
>    抱怨的几乎全是作者名)。
>
>    🔴 **配套发现:被注入的规范名本身可能就是坏的,而且会逐段复制。**
>    `artists.name_i18n` 里 Cézanne 的 zh-hant 是「保羅**施傘**」(正解 塞尚)、
>    Michelangelo 的 fr 是「Michel-Ange **Buronarroti**」(Buonarroti 拼错) ——
>    坏名字被当权威注入,**每一段正文都抄一遍**,污染面等于该作者的全部段落
>    (实测:施傘 27 段、Buronarroti 11 段)。
>
>    **根因不是"LLM 音译瞎编",是上游 + 回退链**(2026-09-01 查清后订正):

> 23. **批量改动的 dry-run 必须按「改动类型」分桶,不能只给样例**(2026-09-01 添)。
>    样例是**自己挑的**:显示名清洗那次打了 12 条样例、全是「剥括号」类,

>    打出各类计数,异常类会自己跳出来问"为什么会有这一类"。
>
>    同一个方法在后续三次拦住错误,值得逐条记:

> 24. **清洗函数的错误会随每次回填静默累积,且永远没有报警**(2026-09-01 添)。
>    `_clean_i18n` 用 `v.strip("《》\"'…")` 剥外层引号 —— 但 **`str.strip(字符集)` 的语义是
>    「两端各自独立地剥」,不是「剥成对的包裹符」**。引号在标题**中间**时(引用某个名号)
>    会被吃掉一侧:`Coupe à décor dit "grain de riz"` → `…"grain de riz`。
>    每跑一次 names 回填就多毁一批,**没有任何报错、没有任何指标变动**,
>    prod 累积到 737 个字段才被一次无关的批量操作顺带暴露。
>    → ① 裁剪/剥离类操作先问一句:**"它会不会只削掉一侧?"**
>       stdlib 的语义要对着意图验一遍,不能望文生义;
>    ② **存量数据的缺陷要定期普查,不能等用户报** —— 这类损伤对用户是"标题有点怪",
>       没人会专门反馈,但它会一直长;
>    ③ 剥离一律**白名单**(同第 20 条):显示名的尾部括号只剥馆藏编号/生卒年/
>       作品类别或作者名,**标题自带的括号必须留**
>       (高更《餐（香蕉）》、Bruyn（長者）——剥掉就成了另一件作品/另一个人)。
>
>    🔴 **配套:同一个判据在不同语言里可能是反的。**
>    引号:德语 `„text“` / 波兰语 `„text”` / 英语 `“text”` —— `“` 在德语里是闭、英语里是开。
>    判不准的一类**整类不动**(43 个 `“”` 不配对的标题就是这么留下的),
>    宁可漏,不可伤。同第 18 条的"阈值一刀切前先看是否该分档"(CJK 一致性天然低于拉丁语系)。
> 25. **归一化在消除噪声的同时可能消除信号 —— 而且可能正好是你要检测的那一类**
>    (2026-09-01 橘园第二批添)。这是第 14 条的**配重**:14 说「比对前必须归一化,
>    否则对特定语言系统性误判」;25 说「归一化的每一步都要问:它对哪些语言删掉的不是噪声」。
>
>    实例:一致性打分的归一化第②步「去变音符」(为 `Tómate`/`Tomate` 而写)对日语同样生效 ——
>    NFKD 把 `デ` 拆成 `テ`+U+3099(浊点),浊点是 combining 字符,于是被删。
>    实测 `アメデオ` vs `アメテオ`、`ばば` vs `ぱぱ`、`だいがく` vs `たいかく` **全部得 1.000**:
>    **日语浊音读错这一整类错误,对一致性检查完全隐形。**
>
>    🔴 **要害不在日语,在于它瞎的位置。** 音色配方定 ja 用 EN 种子的**唯一理由**就是
>    「ZH 种子浊音念错(じっくり→つっくり)」—— **把关那条决策的自动闸门,恰好瞎在那条
>    决策所依据的维度上**。当初能发现是靠人工逐字看转写,不是靠这个函数;
>    这个洞从来没被这个工具自己发现过,是绕过它才看见的。
>
>    → ① 写归一化时**逐步列出「这一步对哪些书写系统生效」**,别只验手头那个语言;
>      变音符、连字、大小写、全半角、简繁,在某些语言里是装饰,在另一些语言里是音位/语义。
>    ② 修归一化**必须跑控制组**(同第 21 条):拿真实语料逐条比对新旧结果,
>      **差异必须只落在目标维度**。实测教训:第一版修法图省事用了全局 NFKC,浊点是合回去了,
>      但顺带把谚文 Jamo 也合成音节(`한`→`한`,长度 3→1),**ko 的 12 条跟着一起变** ——
>      控制组当场抓住。改成只对假名定点重组后,127 条里只有 ja 的 13 条变化。
>    ③ 修好后按第 18 条重跑全量:本例 13 条 ja 最大变化 -0.009、零条新暴露问题 ——
>      **「这个洞在这一批没造成漏放」和「这不是洞」是两回事**,前者是结论,后者是侥幸。
> 26. **你以为你在量 A,其实在量 B —— 判据的名字不等于它实际在查的东西**
>    (2026-09-01 问答闸存量翻案添)。第 20 条说「内容闸看不见形式缺陷」;
>    26 是它的镜像:**内容闸会把形式偏好当成内容缺陷去拦**,而它报出来的字段名
>    仍然叫「不忠实」,于是下游把它当内容问题处理,越修越偏。
>
>    实例:忠实度闸(`check_faithfulness`)本该查「译文说了英文没说的事吗」,
>    实际拦下来的理由却是这些 ——
>    - `Q17190953 it`:"Untranslated word 'anonimato' should be 'anonimato'"(**建议与抱怨字面相同**)
>    - `Q3793237 ko`:"'Canal du Loing' 未翻译"(法语地名,本就该保留)
>    - `Q770649 pl`:"'Tiara Sajtafernesa' 是英语没翻译"(那是波兰语)
>    - `Q2985455 pl`:"'pana Bertin' 用得不一致"(称谓风格,与忠实无关)

>    它查的其实是**翻译完整性/风格**,不是忠实度。两件事被压进同一个布尔值,
>    而这个布尔值决定内容发不发。后果:第 22 条把规范名喂给检查侧之后误判大幅下降,
>    但**没消除** —— 剩余 213 条里仍有 `Le Guerchin`(Guercino 的法语规范名)、
>    `Scènes des massacres de Scio`(德拉克洛瓦原题)被判成"错译"。

>      ② **定期抽样读拦截理由本身**,而不只看拦截率 —— 拦截率正常不代表拦对了地方。
>      ③ 判据跑偏时,存量的 needs_review **不能当内容缺口结案**(呼应第 15 条订正)。
>
>    ✅ **已修(2026-09-02,PR #435/#436)**:忠实度闸改为只判事实,并显式声明"不判翻译
>    完整性,语言由别处检查" —— 因为**语言混杂本来就有 `lang_detect` 独立判**
>    (`qa_suggester` 的 `lang_ok` / `translator` 的 `_lang_ok`,两处都会 and 起来),
>    压在忠实度里是重复的、且比统计方法更不可靠的第二道。
>    重判存量 169 条非英语问答 → 翻案 86 条,非英语问答挂起率降到 0.8%;
>    拆开后判定也更稳(重判抖动率 2.4%,此前 13.3%)。

>    挂起 40 条(2%→45% 通过)、已发布 30 条(100%→100% 零误伤)、
>    **人为破坏 15 条(改年份/塞捏造事实)→ 0% 通过、零漏网**。

>    放宽判据的每一次改动,都必须证明它还拦得住本来就该拦的。
>    配套:**职责移交要验证接收方真的接住了**(新增测试
>    `test_language_gate_catches_what_faithfulness_stopped_judging`),
>    否则"拆开"和"把检查丢了"看起来一模一样。
>
>    🔴 **配套:统计口径也会「量成别的东西」,而且更隐蔽。**
>    本次第一版 census 按 `(object_id, sort)` 把英文和译文对齐,算出"276 条翻译侧判定"
>    —— 错的。译文的 `sort` 是按**英文已发布行**用 `enumerate` 重新编号的
>    (`persist_suggested_questions`),英文 sort=1 的那条在法语里是 sort=0。
>    对齐键同名不同义,数出来的每个数字都错位。改对后是 **415,且 100% 是翻译侧判定**
>    —— 结论的方向都变了(从"一半是内容缺口"变成"一条都不是")。
>    → 跨表对齐前先**验证对齐键的语义**:找一条已知样本,人工确认两侧配对正确,
>      再让它去数几百条。本例的验证是"译文行数 == 英文 published 行数",
>      4683 个(对象,语言)对零例外。

> 27. **判定类 LLM 调用必须 temperature=0;但 0 也不等于确定**(2026-09-02 接地闸添)。
>    判定是分类不是创作。此前接地闸(`check_section`)与忠实度闸(`check_faithfulness`)
>    跟生成/翻译共用 `default_complete` 的 `temperature=0.3`,于是判定带上了随机性:
>    **同一条内容三遍重跑,13.3% 会给出不一致的结论**(prod 英语问答 120 条实测)。
>    这类噪声不报错、不进任何报表,只会在库里静默积压成"看起来像内容缺口"的挂起行。
>
>    ⚠️ **但换成 0 之后两遍一致率是 95%,不是 100%** —— OpenAI 的 `temperature=0`
>    不保证确定性。所以:
>    → ① 判定通道一律传 `temperature=0`(生成/翻译保持 0.3,它们要的就是多样性);
>    ② **批量重判照旧多遍取交集**(第 21 条),别因为设了 0 就省掉这步;
>    ③ 测试要守**装配**(谁拿到了确定性通道)而不只是签名 ——
>    "函数有 temperature 参数"和"闸真的用了 0"是两回事,后者才是会坏的那个。
>
>    副产品:同一个抽样还证伪了一个看似合理的假设 —— "问答答案 99.6% 是 1-2 句,
>    存活率阈值 0.6 退化成一票否决,所以短文本被系统性误杀"。阈值退化是真的
>    (1-2 句必须全过),但它**不是**挂起的主因:实测 1 句通过率 22%、2 句 25%,
>    几乎无差,而 published 组同样 74% 是单句、通过率 93%。
>    → **机制上讲得通 ≠ 它就是主因**。归因前先按该维度分组比一次数据。

> 28. **内容挂起不等于内容缺口;但"重生成到过闸为止"是作弊**(2026-09-02 内容缺口收尾添)。
>    prod 928 条英语正文段挂起,一度被当成"材料不足、要补材料源"。实测三组
>    (真缺口/可翻案/已发布)的材料**几乎完全一样**(material 中位 13244/12865/14167 字符,
>    wikipedia 覆盖 87%/90%/92%,wikidata 事实数 8/9/8)——**材料丰富度根本不是区分因素**。
>    真凶是那批内容 2026-07 一次性生成时 `temperature=0.3` 的**生成质量波动**:
>    写得脑补多的那次被接地闸删光,闸判对了,换一次生成就写得出接地的版本。
>    → 判"是不是真缺口"要**比较各组的材料**,不是看挂起率。
>
>    **首次重生成的通过率 = 材料能支撑的真实水平**(实测 background 89.2%、
>    facts 79.7%、significance 49.4%),差异来自 role 与闸的兼容性:
>    `analysis`("笔触/光色/构图"——站在画前看得出来)属闸放行的 IMPRESSION/FRAMING,
>    通过率 99%;`significance`("改变了什么、影响了谁")全是可核查事实主张,材料里罕有。
>    🔴 **订正(2026-10-14)**:analysis 的 99% **不是内容站得住,是闸的盲区** —— 旧写作要求要「笔触/运笔/技法」,
>    照片和材料给不出,模型编的外观与技法句被闸当印象类放行。P1-9B 只读评测 30 件:闸放行的 analysis 句里
>    判官标出约 1/3 无出处,有看图描述的件同样在编笔触。改成「技法只在材料明说时写」后,有看图描述的件 29→3 句。
>    **通过率高可能只是闸看不见,不等于内容好。**
>
>    ⛔ **但对同一批内容跑第三次就是抽奖** —— 生成有随机性,试的次数够多总有一次蒙混
>    过闸。那不是内容变好,是用随机性绕过闸,与"正确性靠构造、宁缺毋滥"正相反。
>    **课题的终点是「闸拦下来的都拦对了」,不是 needs_review 清零。**
>    真要再降,出路是补材料源或换更强生成模型,不是重跑。
>
>    配套两条操作纪律:
>    ① **只重跑挂起的,已发布的一概不碰**。对照实测已发布内容重生成有 15.6%
>       (significance)/5%(facts) 会翻黑 —— 不设边界的"全量重跑"会毁掉现有好内容。
>    ② **整组替换的写入要有"净损失保护"**。问答译文是 delete+重建
>       (`persist_suggested_questions`,sort 按英文已发布行重编号,只能整组来),
>       新译文过不了闸就落成 needs_review、用户反而少看到内容。加了"新 published 数
>       < 旧的就跳过、保住旧的"之后,全量 790 组里**实际触发 6 组**。
>
>    🔴 **补充:「改输入后重试」与「不改输入的重生成抽奖」是两回事,不受本条约束 ——
>    但仅当同时满足**(2026-09-05 音频改措辞实验添):
>    ① 改动针对**已诊断出的具体缺陷**(逐字定位到问题位置,不是盲改),且有**跑满样本的
>       前后分布对照**证明改动确实移动了通过率 —— **单次通过是运气不是效果**
>       (实例:某候选改法过了一次 0.902,跑满 5 次中位只有 0.885,按 MAX_TRY=3 算
>       三次全废概率仍有 30%);
>    ② 落地的产物是按**标准流程、真实阈值**过闸的,不能因为整体中位提升就豁免单件阈值,
>       更不能为了让它过而放宽阈值。
>    三条都满足 → 属本条自己写明的合法出路"补材料源",不是抽奖;缺一条 → 退回抽奖范畴。
>
>    ⚠️ **改输入必须重过它原本要过的**所有**闸,不只是你当前盯着的那道**
>    (2026-09-05 实测,代价是一条已灌入 prod 的音频被撤回)。
>    实例:为让 TTS 过一致性闸,把日语正文的 `197×1690 厘米` 改成"约 2 米×17 米"。
>    音频侧一致性闸通过、通过率还从 1/5 提到 2/5 —— 但那是**面向用户展示的正文**,
>    重跑忠实度闸判 `False`("dimensions are altered from 197 by 1690 centimeters
>    to approximately 2 meters by approximately 17 meters")。改动为过 A 闸而在
>    B 闸留了洞,**而 B 闸根本不会被触发,因为改动是手工做的、不走内容管线**。
>    - 判据:问「**这段文本原本归哪些闸管**」,不是「我改它是为了过哪道闸」。
>      **手工改内容尤其危险** —— 走管线的改动会自动过闸,手工 UPDATE 不会。
>    - 优先级:**上游内容的正确性不能拿去换下游产物的过闸率**。约数确实更好念,
>      但这个取舍已被"正确性靠构造、宁缺毋滥"定死。改回精确数字后音频三次全败,
>      **接受哑段**才是正确结局 —— 上游正确 + 下游缺失,好过上游被污染换来下游齐全。
>    - 这次绕过了**所有**自动防线(手工改不触发管线闸、音频闸只管音频),
>      发现它靠的是人工评审提问。凡手工改 published 内容,**改完手动补跑一次
>      该内容归属的闸**,别指望有东西会替你跑。
>    **补记(2026-10-10,修好输入后的存量回刷)**:生成的**输入** bug 修好后,存量要不要回刷先小样本 A/B,
>    量的是"新内容是否真的更好",不是"新输入进去了没有"。证据包 bug(#883)修复后抽 10 件按新代码重生成:
>    缺的具名事实只有 2/10 被正文用上,可发布段落 1 件变多、5 件变少、4 件持平;152 件里 136 件已录讲解音频
>    → 结论不回刷。**"补进材料"不等于"模型会用"**,而回刷本身的波动和音频作废是确定的代价。

> 29. **多次重试折成一条汇总记录时,各字段必须与实际保留的产物同源**(2026-09-05 添)。
>    生成脚本每条产物最多重试 N 次,写成一条摘要:`sharp`/`consist` 取"历史最优的那次",
>    `lenratio`/`atempo` 却是循环残留的"最后一次"值,而磁盘上保留的失败产物本身是
>    "最后一次"的文件 —— 三者本应描述同一份产物,实际来自三次不同尝试。
>    **只在失败条目上错**(成功条目提前 `break`,三者天然同源),所以整批统计完全正常,
>    从汇总层面根本察觉不到。
>    后果不是脏数据,是**误诊**:某条失败记录写 `consist=0.06`(读作"内容彻底跑偏、
>    无解"),拿磁盘上那个文件重算实为 `0.79`(读作"边缘失败、改措辞可能有救")——
>    险些据此把一条其实能救的内容判死。
>    → 摘要记录的每个字段必须来自"**实际保留下来的那次尝试**"(通常是最后一次,
>      因为磁盘只留最后一次);确需"历史最优"用于诊断,单独存进 `tries` 数组,
>      不混进顶层字段。
>    → 通用推论:任何"多次重试 → 写一条摘要"的批处理,先问一句"**摘要里的字段是否都
>      描述同一次尝试**",**重点查失败分支** —— 成功分支往往因提前退出循环而天然正确,
>      只有失败分支会踩这个坑。
>    (实现见 `tools/tts/batch_record.py`;与纪律 21"批量结论要留原始计数"同源 ——
>    坍缩成单个数字后,没人能倒推它错在哪,包括写它的人。)

> 30. **文档里记录的参考值,若来自"重试直到过闸"的流程,它描述的是条件分布(幸存者),
>     不能当无条件基准去比对新的单次采样**(2026-09-07 添)。
>    配方记录的三条英语锐度参考值 166/184/166,是生产批次里"≥200 打回重试(`MAX_TRY=3`)、
>    直到 <200 才采纳"的产物 —— **高锐度的尾部已经被这道闸滤掉了**。
>    新实验每个条件只生成一次(不重试),测得 176/208/219,逐一对比文档基准发现
>    三次全部偏高(+6%/+13%/+32%),一度判"环境异常、数据作废"。
>    实际上两者统计对象不同:文档基准是**过滤后**分布,新样本是**原始**分布;
>    原始分布均值天然更高,**系统性偏高是选择过程决定的必然结果,不是环境问题**。
>    最危险之处在于它伪装得极像"环境坏了" —— 偏差方向固定、三次全朝上,
>    看起来正是漂移该有的样子。
>    → 用文档/历史记录的参考值做校验前,先问一句:**这个值本身有没有经过门槛、
>      重试或筛选?** 有的话,它只能拿去比"同样跑满那道门槛"的新样本;
>      要比对原始分布,基准本身必须另留一份**过滤前的原始值**。
>    (与纪律 28 补充"单次过闸是运气不是效果、`MAX_TRY` 掩盖真实通过率"同源 ——
>    都是"重试让人只看得见幸存者"的两种表现:28 管**评估改动效果**时单样本不可信,
>    本条管**引用历史基准**时那个基准已被同一道闸污染。
>    与 ⑩ 不重叠:⑩ 说"指标要对你要区分的差异敏感",本条说"参考值属于哪种分布,
>    决定它能不能被拿来比" —— 本例中指标本身是敏感的,错在两个对象不是同一个总体。)
> 31. **容错把"故障"变成了"静默劣化" —— 凡有降级路径的依赖,都必须配主动探活**
>     (2026-09-12 Joconde 断供复盘添)。
>    纪律① 要求单源失败跳过继续,这是对的:少一个源=内容薄一点,远好过整馆停摆。
>    但它的另一面是**上游死掉不再是一次故障,而是一条 warning 加两个月的悄悄变薄**。
>    实测:Joconde 老 API 2026-07-22 断供,日志里只多了些 warning,没有任何东西变红、
>    没有任何指标变动,**整整两个月没人发现**,期间生成的内容全少一路材料,
>    最后是靠一次无关的排查顺带撞见的。
>    → ① **每个可降级的外部依赖都要有一个每天问一次的探针**(cron + 非零退出)。
>       推送式的报错不会来 —— 容错的全部意义就是不让它来,所以只能主动去问;
>    ② **探针走真正的生产调用路径**(`source.enrich()`),不自己拼 HTTP 请求。
>       自己拼的探针会与生产代码漂移:上游改了列名时它照样 200 绿着,
>       而真正的 enrich 拿到一堆 None。**走真链路 + 断言金标样本的关键字段非空**,
>       才能同时探到"域名死了"和"字段名改了"两种死法 —— 后者往往更隐蔽,
>       因为它不触发任何异常(同第 24 条:没有报错的损伤会一直长);
>    ③ **探针必须自证判断力**(同第 18 条):喂一组已知坏输入,断言它确实会喊 FAIL,
>       并让"探针自己坏了"与"源死了"用不同退出码 —— 处置完全不同,
>       而一个恒说"一切正常"的探活脚本比没有探活更糟:它让人以为这件事有人看着。
>
>    🔑 **配套:外部依赖的时间线不能信公告,要信自己的库。**
>    文化部公告的关停日是 2026-06-01,实际断供是 07-22,**差 7.5 周**。
>    按公告日划线会把 6/1–7/22 之间正常富化的约 80 件误判成"缺材料"。
>    最精确的断点探针是**本源最后一次成功写入是什么时候** ——
>    按日统计命中率会给出一个干净的阶跃(07-22 当天还 100%,07-26 起 0%),
>    比任何外部公告都准,而且是你自己的数据。
>    (与 ⑩ 同族:监视器的沉默被读成一切正常。⑩ 管"指标要能动",本条管"根本没有指标"。)
>
>    🔑 **补记(2026-10-05 识别缓存三个月未生效,#826)**:降级分支吞掉的不一定是"依赖坏了",
>    也可能是"**代码写错了**"。`_get_redis()` 用 `except Exception: return None` 包住了
>    `from app.services.cache_service import get_cache_service` —— 这个函数**从来不存在**,
>    ImportError 被当成"Redis 不可用"静默降级,prod 自上线起 **0 条 `engine=cache`**:
>    同图重发重算(多付 AI 调用)、匿名同图重拍再扣次,而 Redis 本身一直健康。
>    → ④ **降级分支只捕依赖故障**(连不上/超时),`import`/属性/参数这类**代码错误必须炸**,
>      不许和依赖故障共用一个 `except Exception`;
>    ⑤ 探活看**业务信号**:"这条路径被走过多少次"长期为 0 本身就是告警(缓存命中数、某引擎占比)。
>      本例就是评审读代码时看到的,不是任何监控 —— 三个月里没有一个数字变红。
> 32. **用来论证判据的统计,必须就是那个判据本身的命中数**

> 34. **权威来源已有的字段,不要再让模型从非权威渠道提取一遍**

>      「受影响的馆 × 件数 × 会作废的音频条数」,由用户确认。

> 44. **Wikidata 按查询形状选接口:单实体属性走 Action API(`wbgetentities`),批量/条件查询才走 SPARQL(WDQS)**(2026-10-10 #885 添)。

>    补跑同 91 张照片的现行 AI 文字链才得到真基线(库外误给候选 15/59)。与纪律 32(论证用的统计必须是判据本身的命中数)同源:
>    32 管「数的是不是这个判据」,49 管「对照组取样是不是同一个口径」。
> 50. **分级补救的管线里,「提前跳过更贵步骤」的门槛只能设在结果已定处**(2026-10-12 #904 添)。
>    识别原先「全帧+画框 ≥LOW 就不跑裁块」—— LOW 只是「够出候选」,结果还没定;画框给错件刚过 LOW 就把裁块的正确答案挡住。
>    改成「<HIGH(直判线)就继续」后评测集 6 张全变好、弄坏 0。任何「够用就停」的分级流程都先问:停在这里的结果,还会不会被后面改写?
> 51. **生成任务要求写的内容必须是材料能满足的,并显式允许留空**(2026-10-12 #915 添)。
>    「作品意义」段原要求「影响了谁/为何重要」,冷门件材料里没有 → 模型写套话论断 → 闸删空(9-07 起 388 段挂起里 370 段删空,白生成白翻译)。
>    改成「只写材料明说的影响/地位,没有就返回空串,不推断、不写套话」后 A/B 30 件:发布 9→16、挂起 21→5、主动留空 9。
>    这是「宁缺毋滥」在 prompt 层的落法,与纪律 35(禁令长在它约束的那一拍上)成对:**段落职责要可由材料满足,留空要写进那一段自己的职责里。**
>    **补记(2026-10-14,两件事)**:① 上面的「发布 9→16」**在 prod 没有成立**:10-12 上线后 prod 新生成 0 段作品意义,
>    评测里同组合 89 次留空 78 次 —— 小样本 A/B 的结论,上线后要拿 prod 实际产出复核一次。
>    ② 本条已推广到 background/analysis/facts/material-technique/significance 五段(#954,评测方法见纪律 53);
>    摄影/装饰艺术用的 photographer/context/maker/use 四段还是旧写法,上这类馆前照做。
> 53. **同一次调用一起生成的多段,改其中任何一段的写作要求,评测必须覆盖全部段**(2026-10-14 #954 添)。
>    深度段由一次调用生成(`generate_canonical`),各段要求彼此可见。P1-9B 只改了四段,**没动的作品意义段**
>    从 88% 留空变成几乎每件都写套话;把四段中任一段单独换回旧写法都恢复不了(30 次里留空 0–3 次)——
>    效果来自几段要求的组合,无法逐段归因。
>    → ① 对照组与实验组都记录**全部段**的发布/挂起/留空与无出处句,不只看改动的段;
>    ② 复用 `scripts/eval_section_roles.py`(两组共用同一份 guide、过现行闸、gpt-4o 判官复核放行句;只记 `llm_usage`,不写业务数据);
>    ③ 判官标出的只是候选,人工逐条对材料核过才算数(本次 134 条里约 1/3 是解读、轻度修饰或误标)。

## 音频批量生产与灌入(引擎无关;任何自托管/云端引擎都适用)

> 本节只写**与引擎无关的流程与约束**。具体某个模型的调参配方(种子、cfg、音色指标)
> 见 `tts-voice-production-recipe.md`,那是可替换的实现;本节是稳定的接口面。
> ⚠️ **本节采用独立的圆圈序号,不与全文「纪律 N」共享编号空间**——已知撞号三处:
> **⑪**(本节="排队前先做文本体检",§上新馆配方="小馆 popularity 排序失真")、
> **⑫⑬**(本节="合格判定必须可校验"/"重试两轮为限",§工程与运维纪律="不可逆批量
> 操作的护栏"/"替换已有内容必须过质量闸" —— 后者被 `material.py` 等处的代码注释按号引用)。
> **代码注释引用时务必带上节名**,只写「⑪」「⑫」指代不明。

**① 三段式分工(生成机永不碰 DB 和 R2 凭证)**

```
① VPS 出队列   audio_queue_cli.py plan --museum X --langs ... --json > jobs.json
② 生成机产文件  严格按 jobs.json 的字段命名,不自造规则
③ VPS 灌入     audio_ingest_cli.py --jobs jobs.json --dir ./out --engine <名>
               (默认 dry-run;确认无误再 --apply)
```

**幂等按 `audio_engine` 判断**:已是目标引擎的直接跳过,所以重复执行无副作用。
**修了生成侧的 bug 要重灌时加 `--force`** —— 引擎没变,坏的是产物,幂等会挡住修复。
`--force` 只跳过幂等,质量闸与偏差检查照常跑。
自托管生成跑在另一台机器(如 Mac mini),那台机器**不该也不方便直连 prod**。
这样分工的收益:生成侧零凭证、零 DB 依赖;灌入侧统一过闸、统一写 `audio_engine` 标记。

**② 文件名约定 = `{qid}__{language}__{section}.mp3`(双下划线)**
- `section` 取值:`guide` / 深度模块 code / `qa_{sort}` / `artist_bio`
- ⚠️ **`artist_bio` 的 qid 是作者 qid**(音频按作者共享一份,同作者的多件作品复用)
- ⚠️ `qa_{sort}` 的 sort 是**库里的 sort 值**,不是生成侧自己的编号
- ⚠️ **QA 音频是「问+答」连念**(`f"{question}\n\n{answer}"`),分开念会内容对不上、
  且质量闸按问答总字数估时长会判太短
- **命名不要自己推导,一律从 jobs.json 的字段拼**——队列给什么就用什么,零猜测

**③ 比特率必须与质量闸的假设一致(当前 160 kbps)**
质量闸用「字节数 ÷ 比特率」估时长(刻意不引 ffmpeg,要跑几万次)。若产出用了更低的
比特率,估算时长会被系统性低估 → 误判为"截断"。实测:96 kbps 会让韩语 ratio 掉到
**0.44**(门槛 0.45)直接被拒,其余语言的安全余量也被吃掉 40%。
**推论:改比特率 = 改质量闸的前提,两者必须一起考虑。**

**③b 懒生成引擎 = Google Chirp 3 HD(2026-10-15 起,替换 tts-1)**
- 任何引擎落库的 MP3 **都必须 160 kbps**(同 ③);Google 只给 32k MP3,所以要 PCM 自己编(`app/services/tts_mp3.py`)。
- 声音/语速表在 `app/services/tts_service.VOICES`(按语言固定;`/tts/generate` 的 `voice`/`speed` 参数保留但忽略,倍速在 App 播放端做)。
- 送 Google 前必须过 `tts_text.split_sentences`:流式合成会静默吞超长句句尾,切点要改成句号。
- `audio_engine = "google-chirp3-hd"` 的音频算「待升级」,VoxCPM2 队列照常替换。

**④ 上量前先做端到端小样本(1-3 件),不要一次灌全量**
橘园试点(3 件 × 10 语)一轮就暴露了三个真问题:队列没过滤发布状态、校验函数的归一化
缺陷、生成机的显存泄漏。**这些在"生成 30 段"时是小麻烦,在"生成 3 万段"时是灾难。**

**⑤ 幂等与断点续传是必须特性,不是优化项**
批量音频动辄十几小时,中断是常态(网络/重启/OOM/手误)。生成侧要"见到已存在的合格
文件就跳过",状态实时落盘;灌入侧本身幂等。**没有这条,中断一次就得从头再来。**

**⑥ 长时间批量要分块换进程**(长驻进程的显存碎片/泄漏,与模型无关)。具体硬件的实测与分块大小
见 `tts-voice-production-recipe.md` §七(本节只留与引擎无关的约束)。

**⑦ 灌入是 prod 写操作 —— dry-run 报告 → 人工批准 → apply**
`--apply` 前必须先看 dry-run 的过闸统计。橘园试点 28 段全过闸后才执行写入。
**重灌场景要跑两次 dry-run**:先不带 `--force`(应当全部 `already_done`,证明幂等这道
防误覆盖的锁还在),再带 `--force`(看质量闸判定)。两次都对了再 `--apply`。

**⑧ 语速对齐是生成侧的责任,落库侧不是安全网**
质量闸的 `CHARS_PER_MIN` 与生成侧用的是同一套字/秒基准,但它刻意放宽到
`ratio ∈ [0.45, 2.2]` —— 只拦数量级错误(截断/无限重复),**+15% 的系统性偏快稳稳通过**。
实测橘园 28 条 guide 全部偏快 15%(某语言 +23%),质量闸一条都没拦下,是用户耳朵先发现的。
→ 凡"目标形态由基准定义"的产物(语速、图片尺寸、字数),**对齐必须在生成侧做完**;
落库侧的宽闸是防灾,不是防偏。
**同一条原则的第二个实例(2026-09-08):响度。** 全量实测已灌入的 568 条,同一件作品
同一语言内部的响度极差中位 4.1 LU、最大 15.3 LU(76% 的组 >3 LU)。生成侧三道质检门
(锐度是比值/一致性是转写/长度比是字数)与灌入侧的 `check_audio` **全都对音量免疫**,
一条都拦不下。→ 已在生成侧加纯增益归一(配方 §二「响度对齐」)。
**踩第二次说明这是个类,不是个案:新增任何批量产物,先问「它的哪些维度没有任何一道闸在看」。**

**⑧-b 验证灌入结果:查 DB 的 `audio_key` + R2 对象大小,别走 `/content` 端点**
`/content` 按设计**从不下发 `audio_url`**(付费墙,只给 `has_audio` 布尔;音频链要走带鉴权的
`/audio`)。拿 `audio_url` 去验会得到一片假失败 —— **这个坑 2026-08 踩了两次**,而且契约
`default_guide` 字段处早已注明。教训不只是"看文档",而是**提示要放在会被读到的地方**:
排查灌入的人打开的是灌入章节,不是字段字典。
→ 正确做法:比对本地文件与 R2 对象的 **md5**(不是字节大小,理由见 ⑩),
既绕开鉴权、又验的是落库真相、还不受任何缓存干扰。
脚本 `backend/scripts/verify_audio_md5.py`(在 prod 容器内跑)。
⚠️ **三类段落的 audio_key 在三张不同的表**(section / qa / `Artist.bio_audio`),
核对必须三张都查 —— 旧版脚本只查 section,对 qa 与 artist_bio 完全失明**而报告照样全绿**
(2026-09-14 卢浮宫七语那批 285 条里,这两类占 111 条 = 39%)。
旧脚本还只在生成机本地(`~/tts-lab/`)、用字节大小校验,两个问题一起修掉了。

**灌入后同样要三方核对**(2026-09-04 添):CLI 报的 `written` 数 ==
DB 各类计数的增量(正文/问答/作者介绍分别数) == 逐条 md5 核对通过数。
三条独立路径都对上,才算灌入成功 —— 单看 CLI 自报的 `written` 不足以采信,
它只知道自己写了什么,不知道 DB 和对象存储的终态。

**⑨ 替换会生成新 key(不是原地覆盖),这带来两个后果**
`audio_key()` 带不可推测随机后缀,所以替换后 key 变了:
- ✅ 前端拿到的是新 URL,**不存在 CDN/App 缓存住旧音频**的问题;
- ⚠️ 旧对象即刻成孤儿(存储成本可忽略;回收脚本 `scripts/gc_orphan_audio.py`,护栏见纪律 12);
  换个角度,**孤儿在验证期是回滚退路** —— 把库里的 key 改回去即可。

**⑩ 验证指标必须对「你要验证的那个差异」敏感 —— 否则通过等于没验**
(2026-08-31 添)重灌 3 条繁体音频(换了音色种子)后用字节大小校验,报告"30 条一致、
0 条不符",看起来完美 —— 但那 3 条替换前后的字节数**一模一样**:CBR mp3 的字节数 =
时长 × 比特率,而语速对齐把两版的目标时长压成了同一个值。**换种子改变了每一个采样点,
却一个字节都没多**。改用 md5 才真正验到内容。
→ 选校验指标前先问一句:**"如果这次改动失败了,这个指标会不会变?"** 答不上来,
这个指标就不能用。同类:改文案后比对字数、改配置后比对文件行数 —— 都可能恒等。
这是纪律 19 的延伸:19 说"两端不能同源",⑩ 说"**指标要能动**"。

**⑪ 排队前先给文本做体检;有问题的藏品/段落不进本批,修完再排**
(2026-09-03 添)音频是**不可逆的重资产**:十几小时机时 + 生成一次永久落库 + 用户直接
听得到;文本是可逆的轻资产,改一次就是几分钱。**让重的等轻的,不要反过来。**
何况文本一改 `audio_key` 就被置 NULL(配方 §七),抢跑的音频等于白跑。

体检查三类,**都要用查询查,别靠翻页看**:

| 类型 | 查法 | 处置 |
|---|---|---|
| **空洞** | 每 (件,语言) 的段数是否相等;`length(btrim(body))=0` | 少几条不害人,但要知道自己少了什么 |
| **挂起** | `status='needs_review'` 分布 | 队列只取 `published`,翻案后必须补跑(配方 §七) |
| **污染** | `museum_objects.artist_en`(**是表的列,不在 `attributes` 里**) vs `artists.name_en`(按 `attributes->>'artist_qid'` 关联) vs `attributes->>'artist_extract_en'` **三者是否同一个人** | 🔴 **剔出批次**,修数据+重生成内容后再排 |

**污染最危险,因为它一切看起来都正常**:音频过闸、音色一致、听感完美,内容却接地在
错误的材料上。2026-09-03 橘园 Q64309678《静物,梨和青苹果》—— 10 语 78 条正文全在讲
"梵高的医生保罗·加歇画了这幅静物"(真作者是塞尚,橘园官网写着)。若不体检就排队,
780 秒错误归属的音频会永久落库,而且**没有任何一道自动闸会拦**:质量闸判时长和语速,
忠实度闸判译文对不对得上英文原文 —— 英文原文本身错了,它一路绿灯。

反过来说,能发现它是因为**闸抓到了不一致**(fr/guide 与 zh-hant/facts 被拦),
所以修复时必须小心:只让各路径"取到同一个人"而不管取得对不对,会把**可检测的不一致
变成不可检测的一致错误**,比不修更糟。→ 见 `material.resolve_creator_qid`。

⚠️ "先把能跑的跑了,坏的以后再说"是对的,但坏的**不许捎上** —— 批次里混一件坏的,
事后要么整批重灌,要么留一件永远对不上的。**剔出来的成本是零,捎上的成本是重来一遍。**

🔴 **体检查询查出一片空值时,先怀疑查询,不要判定"这个字段没用了"。**
(2026-09-04 实测)我把 `artist_en` 当成 `attributes` 里的键去取,10 件全是 NULL,
于是记下"字段名不对或已不再使用",**差一点去"修正"这条本来正确的规程**。
它其实是 `museum_objects` 的列。空结果与"检查通过"在输出上无法区分 ——
**任何体检查询都要先在一条已知有值的记录上验一遍取数路径**,再拿它去扫全批。
(同一族错误:监视器的沉默被读成一切正常。见纪律 ⑩ 与 §四的判定工具纪律。)

**⑫ 只有生成侧判定合格的产物,才允许出现在灌入目录(2026-09-04 添)**

灌入端的 `check_audio` **只判时长比例与替换偏差,不看锐度、不看内容一致性**。
生成侧唯一的质量判据(过没过闸)在灌入侧没有任何对应护栏 —— 目录里放什么它就传什么。

实测后果:一条从未过闸的音频(`Q3937645/ja/qa_0`,一致性未达 0.90)灌进了 prod,
而当时**md5 逐条核对 127/127 全过** —— 核的是"上传的和本地一致",
**验不出"本地这条本身没过闸"**。校验方向错了一维,通过得毫无悬念。

→ 生成脚本必须把三次仍不合格的产物**移出灌入目录**(移到 `_rejected/`,
不是删除 —— 删了就查不出失败原因,实测当天就撞上)。
→ 但"文件放对位置"是**约定**不是**校验**。上规模后同时操作多个输出目录、
多轮重跑、跨机传输,拷错目录只是时间问题。

✅ **已落地(2026-09-04,#478)**:判定结论随文件一起交付并被灌入端核验。
载体就是 `_state.json`(生成侧本来就写,现在多记一个 md5),
灌入端读 `--dir` 下的它,三类拒绝并计入独立的 `unverified` 计数:

| 拒绝原因 | 对应的现实失误 |
|---|---|
| 判定记录里没有这条 | 拷错目录 / 别批残留 |
| `ok != true` | 生成侧三次都没过闸(漏进 prod 那条正是这形态) |
| md5 与判定时不符 | 传输损坏,或文件被换过 |

`--apply` 却没有 `_state.json` → **报错退出**。悄悄降级成"不校验"等于没装护栏,
失败方向必须是拒绝;外部引擎产出确实没有该文件时,显式加 `--allow-unverified`。
老批次的 `_state.json` 没有 md5 字段 → 跳过这一项,不把它们全判成不合格。

**⑬ 重试两轮为限,之后接受诚实缺口**

实测收益曲线(2026-09-04,570 条):脚本内每条已重试 3 次;此后**整体重跑第一轮
救回 5/8,第二轮 1/2,第三轮 0/2**。前两轮吃的是生成随机性的红利
(有过连续 4 次同一坏值、第 5 次通过的实例),再往后是真缺陷。
→ **两轮为限**,剩下的按纪律 28 记为内容/质量缺口,不许重跑到过闸为止。
上百件规模下这条决定了会不会在个别条目上无限烧机时。
**缺口与"机器判不了对错"的疑点一律记进 `docs/ops/audio-followups.md`,攒够一批统一处理** ——
逐条追要么打断跑批、要么被忘掉;而单条看是"这句念错了",攒够才看得出是不是系统性的。

**⑭ 上规模按件灌入,不要攒到最后一次性灌(2026-09-04 添)**

实测节奏:568 条(= 570 条任务 − 2 条按 ⑬ 记为缺口)≈ 生成 11h + 传输 31min(535MB) + 灌入 12min + 核对 12min,
**生成占 95% 墙钟时间**。100 件约 5700 条 → 生成 4-5 天。
攒到最后灌意味着中途任何意外都让几天产出滞留在生成机上,且失败排查面是全批。
→ 按件(或每 N 件)走完"生成→重试→核账→传输→dry-run→批准→apply→核对",
价值尽早落地、故障局部化。
⚠️ 推论:**想提高一次性成功率,该优化的是生成本身(种子/音色),不是流程**。
⚠️ 但「闸拦下的都是真实质量问题」这个前提本身要验:2026-09-14 九条盲听证伪了
英语锐度闸 —— 它拦下的内容人耳判「可接受」,放行的反而有判「不可接受」的,
门槛 200 只是切在一团连续分布正中间。**一道闸的拦截量不等于它的判别力;
在拿它当优化方向之前,先用人耳盲听验一次这道闸测的是不是你以为的东西。**
(依据见 `docs/architecture/tts-voice-production-recipe.md` §四)

**⑮ 灌入前核账(2026-09-04 添)**

```
_state.json 里 ok=true 的条数  ==  灌入目录里的文件数        ← 必须精确相等
原始任务清单条数 − 上面这个数  ==  按 ⑬ 记为缺口的条目数      ← 差额必须能对上
```

⚠️ **第二个等式不能写成"清单条数也相等"** —— ⑬ 明确允许存在诚实缺口,
所以 ok 数**合法地**小于清单数(本批 568 vs 570)。写成三者全等会与 ⑬ 互锁:
遇到 ⑬ 认可的正常收尾也要"停下查",而查不出任何问题。
**要核的是差额有没有解释,不是差额为零。**

这几个数来自三条独立路径(生成侧判定 / 文件系统 / 队列),
对上了才说明没有漏条、没有多带、**没有拷错目录**。任一对不上,停下查,不要开始传输。

**⑯ 起跑前锁定生产脚本版本:先 `git pull`,再开跑(2026-09-12 添)**

长批一跑十几小时,**中途发现代码是旧的 = 那一段白跑**。2026-09-10 卢浮宫 TOP3-10
用落后 3 个提交的本地 `staging` 起跑,缺 PR #521(zh-hant 喂简体给模型),
12 条繁体是**按已知且已修好的缺陷**生成完才发现的。

唯一把它暴露出来的信号是 `_rejected/` 里一条**确定性失败三次**的条目 ——
随机失败会被重试掩盖,只有确定性失败才浮得上来。**别指望质检闸告诉你代码旧了**:
闸判的是产物合不合格,旧代码完全可以产出合格的东西,只是不该长这样。

→ 开批固定三步:`git pull` → 确认跑批入口指向仓库里那份脚本(不是本机旧副本)
→ 把起跑 commit 记进批次日志。
→ 这次的根因是多个 session 共用同一个工作区分支。**并行 session 各切各的分支/worktree。**

## 内容体系（三层 + 模块库 + 证据包）

> **⚠️ 英语轴心（en axis）——核心生成约定,所有生成内容必守。**
> 一切内容(讲解 / 深度模块 / 问答 / 作者 bio)**先用英语生成**(prompt 必须含 "Write in English")→ 三类**接地闸在英语上判** → 再 `translate_object` 翻成 zh/fr/…(各自忠实度校验)。
> **为什么**:接地/事实校验只在英语做一遍,其它语言靠忠实翻译继承 → 省、且跨语言一致。
> **教训(2026-07-02)**:新加 `generate_artist_bio` 时漏了 "Write in English",作者 bio 随材料语言乱输出(en 条存成中/法文),切语言不对。**新增任何生成 prompt 都要强制英文。**
> **不变量:译文的发布状态从属于它的英文源。** 英文段不再 `published`,同段译文必须一起下架 ——
> 译文的正当性正是"接地闸在英语判过一遍"给的,源头没了,正当性就没了。
> 由 `content_repo._upsert_section` 级联保证(所有段落写入的唯一咽喉),**不靠人记得去查**。
> 教训(2026-09-03):橘园 Q64309678 修完作者归属重生成,英文 significance 因整段无材料支持
> 被闸清空,9 条译文原地留存 —— 正文已换成塞尚,significance 还在讲梵高的医生加歇,且仍在下发。
> `translate_object_language` 只翻**已发布**的英文段,所以译文既不会被重写、也不会失效。
> 当时 0 条已灌音频纯属侥幸,再晚一步就会被灌成音频、永久落库。

> **⚠️ 多语显示名规则(title / artist.name)——语言无关,核心约定。**
> 任何**显示名**(藏品标题、作者名)按请求语言解析,走固定回退链:
> **① 该语言的权威标签**(Wikidata 多语 labels / 馆方官方标签,专有名词最优)→ **② 从英语轴心机器翻译**(该语言无权威标签时兜底)→ **③ 英语轴心原名**(永不空)。
> **语言无关**:新增语言(de/es/it…)**只加进 `DEFAULT_LANGUAGES` 语言集**,生成时一次性抓该实体全部目标语言的 Wikidata labels、缺的从 en 翻译 —— **同一套机制、零 per-language 代码**。这就是"加语言=加配置"。
> **配套**:**QID 是全系统匹配键**(识别/查询/去重/跳转都用 qid);显示名纯展示,名字回退绝不影响匹配。避开脏格式(如 Joconde 的 "Lastname First (dates)")。
> **非 Wikidata 条目的身份(✅2026-07-16 #255 定)**:无 Wikidata 条目的件,qid 位=**合成把手 `<source>-<reference>`**(如 `joconde-000SC010033`)——对外稳定、全系统当 qid 同键用(识别/搜索/跳转零分叉);内部检索按 UUID 回查。`is_wikidata_qid()`(Q+数字)做门控:合成把手**跳过一切 Wikidata SPARQL**(省成本+避免 `wd:<合成号>` 垃圾查询)。**names 配方**:这类件无权威标签可抓 → 直接走显示名规则②(title_en 轴心纯翻译,staging 实证 1038 件×10 语零失败);**无 title_en 则无轴心 → 留空不硬造**(宁缺毋滥)。上新馆接任何非 Wikidata 源(区域目录/官方馆藏库)照此,零核心改动。
> **⭐ 多语字段的读写对称性(2026-07-26 卢浮宫定,两处实测事故)**:显示名的**写入落在 i18n JSON**
> (`attributes.title_i18n` / `Artist.name_i18n`),**读取必须 i18n 优先 + 列兜底,且所有语言维度对称**。
> 不对称 = 数据在库里却到不了用户,而且流程全绿、数字漂亮、无声无息:
> - `title_zh` 早做了 i18n 优先,`title_en` 只读列 → 卢浮宫 **9505/17283 件列空(其中 9497 件 i18n
>   里其实有英文名)**,英文用户看到一半藏品标题空白(#323 修)。
> - 作者本地化名真相源是 `Artist.name_i18n`,馆包却只读 `MuseumObject.artist_*` 裸列(详情接口早用
>   `_resolve_name` 做对了、馆包漏了)→ 卢浮宫 **10041 件作者名中文视图全显拉丁文**。
>

> {列}, 兜底)` 是统一入口,别绕过它直接读列。

> **⭐ 外部标识符必须校验格式,不能盲取 URI 末段(2026-07-26 卢浮宫事故)**:Wikidata 对
> **"未知值"(somevalue,如作者不详)返回 blank node** `.well-known/genid/<32位hex>`,

> 形式返回(blank node / 空串 / 占位符),解析时校验格式、不合格就留空(宁缺毋滥),别让脏 id 进库。

- **第三层 AI 自由问答**(`/ask`,规划):多轮,复用证据包,争议必 hedge。

**模块库(`tabs`,深度内容,降级为"更多内容")** —— 各守互斥 lane,**只补默认讲解没深挖的一面**:

**关键机制(✅阶段2a 已落地)**:① 先生成默认讲解(头条)→ 模块单调用带头条+证据包富属性+锐化 lane"各守职责、深化非复述、只会重复就返空"(生成已从证据包取料)→ 问答最后只补缝。② **动态显示**:空模块不展示(料薄优雅降级,默认讲解是地板)。**深度模块字数按热度分档**(重点件 ×1.5),名作能深则深、薄件天然短;深=用材料具体细节铺开非注水(接地闸+去重兜底)。③ overview 退役(与默认讲解头条重复)。

## 识别（拍照→讲解;✅P1 2026-07-03;✅向量引擎+全局端点 2026-07-11）

**原则（通用,任何馆零代码）:**
- **R1 识别接地第一原则**:AI 视觉输出是**查询不是答案**——候选名必须匹配到真实目录记录才展示身份;不中就诚实"未收录",绝不把模型猜测当事实。(向量检索天然接地:命中的就是目录参考图。)
- **R2 墙签 OCR=权威接地源,但是增强不是依赖**:照片常无签是常态,主路靠画面内容;"引导补拍说明牌"是未收录 UX 的组成部分(`mode=label` 纯转写)。墙签行同时做**馆藏号精确匹配**(归一化后≥3位,编号=馆方主键,命中即满分)。
- **R3 三档呈现**:高置信(≥HIGH)直开讲解页 / 中置信确认卡(1-3 候选带缩略图) / 低置信未收录+引导拍签。**确认卡=免费人工标注**(真实照片→确认QID,数据飞轮)。**GPT 兜底链命中一律走确认卡不直判(同名撞车实证:自画像/The Bathers 精确同名撞他馆无关件),直开讲解页只来自向量高置信(像素证据)。**
- **R4 引擎可替换,匹配/接地层是不变核心——✅已兑现**:主引擎=DINOv2 ViT-S/14 向量检索(参考图库余弦近邻;benchmark 非名作 Top-1 95.8%/库外零误接受,见 2026-07-11 bench spec);GPT-4o-mini+墙签 OCR 降级为**兜底**(无参考图/低分件;调用量从每张必调降为仅 miss)。引擎任何不可用形态(模型缺失/坏图/表空)→ 自动走兜底,绝不 500。
- **R4 补记·AI 兜底=在向量前 5 名里做选择题(2026-10-12 #909)**:向量有排名(最高分 <LOW)时,GPT 拿到**照片 + 向量前 5 名的标题/作者 + R2 参考缩略图**,只回答「是其中第几件或都不是」;选中的那件作**唯一候选**(仍走确认卡、永不直判),自由猜名不再出候选;馆藏号+作者双重吻合直判保留;向量无排名(引擎不可用/空表)才回落旧文字链。`text_trace.shortlist`/`shortlist_pick` 记录。评测集 91 张走 AI 的照片:在库答案进候选 5→19/32、候选含答案比例 15%→40%,库外照片误给候选 15→22/59(用户权衡后采纳)。契约形状不变。
- **R5 需求自适应**:未收录拍摄记 `recognition_demands`(按 馆+感知哈希 幂等计数,全局识别时馆可空;墙签文字=高质量需求) → 目录跟真实需求生长。
- **R6 足迹 vs 归属两轴分离**:到访足迹用物理位置(GPS/App 选馆),绝不用识别到藏品的拥有馆(借展场景两轴背离)。后续落地,原则先立。

**端点(两个,响应同形):**
- `POST /api/v1/recognize`(**2026-07-11 新增,App 主入口**):multipart `image` + query `museum`(slug,**可选**) + `language` + `mode`。不传 `museum` = 全局识别(拍前无需选馆——导航栏识别按钮直达相机);传了 = 只搜该馆。
- `POST /museums/{slug}/recognize`(保留,行为不变):馆域内匹配。**⚠️ 馆域调用不做全局回退**(2026-07-11 裁决:老 App 不读 `museum` 字段,跨馆命中会拿他馆 qid 撞详情 404 死胡同——前向兼容;将来带馆提示要"馆内优先+全局回退"时加显式参数再开)。

响应:`{outcome: match|candidates|unrecognized, match:{qid,title,artist,thumbnail,confidence,museum}, candidates:[{…,score,museum}], label_text, reason, phash}`
——**`phash`(2026-07-13 加法字段)**=该次识别的感知哈希,配套 **`POST /api/v1/recognize/confirm`**(`{"phash","qid"}`,可选 Bearer,永远204,fire-and-forget):确认卡点选时上报,回填 recognition_events.confirmed_qid(**`POST /recognize/reject` 同形**:候选卡「都不是」与 2026-10-12 起直判后讲解页「不是这件?」都走它;**被否定的直判不算足迹、不算在展证据**——判据收紧,字段不变)——**确认卡=标注飞轮**从此有服务端落点(KPI 的 hits=match+确认候选;match 直跳不上报,confirmed 语义=用户确认)。识别每次调用落 `recognition_events`(只存 phash 不存照片;engine 记 vector/vector_crops/text/cache)——**KPI 与展陈证据一表两吃**。museum pack 加法字段 `catalog_count`/`archive_count`(馆页双数字"在线图录N·档案M",**每次请求现场 count**;**2026-10-11 方案 B 起 `archive_count` 恒为 null**——无图件搜不到也认不出,「可识别/搜索」成了假话,App 两数齐全才显示该行 → 隐藏;`artwork_count`(馆包两分支与 `/museums` 列表)= 有图件数;2026-10-04 #804 前曾读 museums.stats 快照,补图后橘园仍显旧值 15——门面数字不读快照)。
——**`museum`=归属馆 slug(2026-07-11 加法字段)**,前端跳详情用它(老 App 不读不炸;新前端解析 `as String?` + 回退)。`outcome/reason` 机器码不译;`title/artist` 按 language 走显示名规则;thumbnail=thumb 档。命中跳详情 → 懒生成/懒翻译/懒补图自动接管。同图重复识别走 Redis 缓存(命中 30 天/未收录 1 天;键 `recog4:{馆或 global}:{RECOG_MODEL}:{language}:…`,换引擎或改识别口径即换前缀/模型名,旧缓存自然作废,见纪律 33④)。**阈值 server-driven**:向量档 `RECOG_HIGH=0.85`/`RECOG_LOW=0.72`(环境变量,由 benchmark 校准,库外零误接受);文字兜底档沿用 HIGH=0.85/LOW=0.5。

**低分自动多裁剪重查(2026-07-11;2026-10-12 #904 触发线 LOW→HIGH)**:全图+画框后最高分 < HIGH 时自动裁 中心60%/35%+四象限+左右半幅 批量重查取最大分,再不中才进 GPT 兜底。**正常近拍照片走快路径零延迟影响**;触发裁剪的照片 +~2s,仍快于其下一站 GPT(2-5s)。已知代价(bench 实测):库外照片经多裁剪误出候选卡比例升高(48%→81%)——确认卡"都不是"出口兜底,可接受。**为什么是 HIGH 不是 LOW**:原先「已 ≥LOW 就不裁」,画框给错件刚过 LOW 就把裁块挡住(《自由引导人民》人群远景:画框错件 0.723 挡住裁块的 0.912)。≥LOW 只是「够出候选」,不是结果已定;**提前跳过更贵补救步骤的门槛只能设在结果已定处**(纪律 50)。评测集影子对比变化 6 张全变好、弄坏 0,候选档约 +0.85s。

**⚠️ 识别优化的优先级原则(2026-07-12 定,真实用户测试得出)**:**App 用户是"有意图取景"的**——想识别某件作品的人会主动找能看清整幅作品的角度,拍歪了自己重拍;合影/极偏构图不是主流场景。Commons 随手拍照片测出的失败案例会高估怪构图的真实占比。**故:不再对怪构图做裁剪/阈值工程加码**(已合并的多裁剪留作免费保险丝);识别精度投入主线=**二维靠参考图覆盖,三维靠多视角图库**(建设策略并入藏品覆盖率机制,另立 spec)。

**识别参照库(与目录共生)**:参考图入库(物化)即嵌入(DINOv2 向量落 `object_embeddings`,生成一次永久落库,model 字段版本化);存量用 backfill CLI。**画作他人实拍(2026-10-12 #910,`role=recog_view`)**:必看/失败画作从 Commons 分类拉他人实拍(画框/人群/书页扫描),**只进识别索引、不进图集/分享/看图描述**(`HIDDEN_ROLES`);入库闸在相似度三段之外加「**在现有索引里更像别的作品 → 隔离**」(Commons 分类会混进别的作品,收进来就串号);`onboard recog-views --qids …`→ 只物化这批件。prod 首批 36 件收 247/隔离 62/删 9,作废音频 0。**雕塑多视角**:Commons 分类(P373)拉他人照片入 `role=view`(≤4张/件,Special:FilePath 规范 URL 保署名链),物化即嵌入——3D 单视角是 benchmark 实测短板(真实照 Top-1 ~33%)的对症药。**view 自动治理(2026-07-13 落地,纯自动无人审)**:Commons 分类混入非本体图(orsay 实测 14%)的清洗策略——view 与该件正面照相似度 **<0.25 自动删**(实测全为垃圾)/**0.25-0.4 隔离**(`role=view_quarantine`:留档、不进索引、不上图集、不计有图)/**≥0.4 入索引**;物化嵌入钩子同规则前置闸(新图入库即治理);错杀极端角度由照片飞轮(Phase 3)补回。**宽幅作品切块(2026-10-04 #806,硬规则:凡宽幅必切)**:识别预处理把整图压成 224×224,长短边比 ≥2 的作品(橘园《睡莲》3:1~9:1)被压扁后,用户拍的局部(手机 4:3)与它几乎不像——**主图长短边比 ≥2 → 沿长边切满短边 4:3 窗(步长半窗)**,每块存 `role=tile`(R2 `images/{qid}/tile-N_large.jpg`,换模型 backfill 按 image_key 重嵌)、一块一向量都指向原件;查询侧不动。tile **不进图集/分享、不计多视角张数**(`HIDDEN_ROLES`)。切块源取 Commons 3840px(large 档 1600 对 9:1 长卷只剩 180px 高)。实测 54 张橘园实拍(SIFT 独立标注):top1 对 27→51、直判 12→38、错认 8→1,橘园其余 110 件 0 件被抢;半高窗 ×7 向量只多对 1 张故不做。**接线**:`onboard images` 物化完自动切(新馆/新件零额外步骤);存量补切 `scripts/tile_wide_images.py <slug> [--dry-run]`(幂等)。⚠️**极相似姊妹作**(《晨与柳树》vs《晴晨与柳树》)切块救不了——参考图质量差的一方会被抢,加对方实拍 view 又反抢回来(实测 +3/-2),这是区分度问题不是覆盖问题。**上新馆配方只有一套,见§上新馆**(识别相关是其中第 4 步及 4a/4b)。⚠️ `names` 首次收全条目时是数千件×10语回填,约数小时级,须在服务器侧 nohup 脱管跑;增量重跑只处理新件。
**计费(2026-07-04 定)**:`match/candidates` 扣 1 次配额;`unrecognized` 不扣(不为失败付费);缓存命中不扣;配额用尽 → **402** `{reason: quota_exceeded}`(先于 GPT 调用,不烧钱)。身份=Bearer 令牌(App 自带)或 `device_id` 参数;两者皆无 → 401 `{reason: identity_required}`。服务端扣费,不再依赖前端自觉调 `/payment/consume`。

**老端点 `/api/v1/recognition` 标记 deprecated**(裸 GPT 猜测当事实,违反 R1;留给老 App,新 App 一律走新端点)。

## 付费墙(现场体验收费,内容永远免费;✅2026-07-28)

> 📎 **完整的身份/权益/付费墙架构见 [`identity-and-paywall.md`](./identity-and-paywall.md)**
> —— 19 条可检验的不变量、端点闸门矩阵、已知取舍、商店适配端口。
> 本节只留与馆 API 直接相关的部分;**改付费相关代码前先看那份**。

**⭐ 唯一执行点在后端,前端 UI 只是它的表达。** 客户端闸只为省一次往返;
老 App / curl / 改客户端都能绕过前端,所以每条产音频/产识别的路径都必须自己过闸。

**通票有 `scope`**:`city:paris`(按馆 `city_en`)/ `country:NL`(按馆 `country`)/ `*`;旧写法 `paris` = `city:paris`。
**城市票还是国家票只是后端配置,改它不发版。** 商品目录(`PASSES`,带十语 `label` 与 `on_sale`)是时长/scope/SKU/
展示名的单一真相源;**前端不认识任何一张具体的票**,商品 ID/票名/天数/覆盖馆全部由后端下发(馆包/402 的 `pass`、
`/me.offers`、`/me.passes`)。上新城市/新国家 = `PASSES` 加一行 + Play 建商品 + 放出馆。详见另一份文档 §3.1。

**免费层**(游客与注册用户完全一致,按 `user_id` 索引;游客=真实 User 行 `is_guest=True`):
- 免费额度 **5 次**(真相源 `settings.FREE_RECOGNITION_QUOTA`,别在任何地方写死数字)。
  它是**一个池子**:拍照识别扣它,在藏品页主动解锁语音也扣它 —— 所以"免费能体验多少"
  只有一个数字,不必维护第二个。
- 语音 = **解锁过的那些作品**的主讲解段,**解锁起 7 天内**可重播(D8,2026-09-29;此前是永久)。
  清单存 `user_benefits.free_audio_qids` = `{qid: 解锁时刻}`;窗口天数由后端 `/me.free_audio_days` 下发。两条解锁路径:
  识别成功当场解锁(写在扣费的同一处);或用户在藏品页**显式确认**后花 1 次额度解锁。
- 浏览/搜索/**完整文字讲解**/预设问答 → 永远免费,不需登录

**必须过闸的端点**(新增任何产音频/产识别的端点,先问它在不在这张表里):

| 端点 | 闸 | 备注 |
|---|---|---|
| `POST /recognize`、`/museums/{slug}/recognize` | 额度 | match/candidates 扣 1;未识别与缓存命中不扣 |
| `GET /museums/{slug}/objects/{qid}/audio` | `audio_access` | 402 `pass_required` |
| `GET .../audio/stream` | 同上 | ⚠️ 播放器直取、**不经 Dio 拦截器**,前端须自带令牌 |
| `POST /content/tts/generate` | 同上 / 通票 | section 模式按 qid;ad-hoc(任意文本)需通票生效 |
| `POST /entitlements/audio/unlock?qid=` | 额度 | 花 1 次额度解锁该件主讲解段;**先扣费再解锁**;幂等;额度为 0 → 402 |
| `GET /entitlements/me?museum=`、`POST /entitlements/activate?museum=` | 按馆 | 带馆 → 只看/只激活**覆盖该馆**的票;不带 = 旧行为 |

⚠️ 上表所有"按票放行"的判断都**按资源所属的馆**判(qid 反查,不信 URL 的 slug),见闸门纪律 7。

**⛔ 内容端点绝不下发 `audio_url`。** `/objects/{qid}/content` 无鉴权(正文免费是策略),
发直链等于拆掉付费墙 —— 音频 key 做成不可推测也白搭,是我们自己发出去的。
只给 `has_audio` 布尔:前端据此显示播放按钮,要听走上表的闸门端点。

**闸门实现的纪律**(都踩过):
1. **判定无副作用**。闸跑在 TTS 生成之前(对的,否则钱已花),而生成可能
   404 无正文/409/503 —— 闸门若顺手写库,用户什么都没听到、权益却变了。
   ⚠️ 旧的 "claimable + 送达后认领" 两档机制已随纪律 5 整个删除,但这条约束留着。
2. **免费额度只有一个数字**(2026-09-19)。此前「免费试听 1 件」与「免费识别 5 次」
   是两个互不对齐的数字:用户识别第二件、点播放被弹墙,观感是"那 5 次是假的"。
   新增免费维度前先问:它能不能**跟着已有的那个数字走**?
3. **「数据行还没建出来」≠「没有权限」**(2026-09-19)。`user_benefits` 是**懒建**的
   (首次 `/payment/benefits` 或首次识别才建)。闸门当年把 `benefits is None` 判成
   denied,而**真实的新注册用户正是没有行的那一类** —— 每个新用户的首体验都是付费墙。
   实证:prod 78 个账号里 35 个没有这一行;免费试听上线至今,19 个用过识别的账号
   认领数 **0** —— 这个功能一次都没成功过,而三道测试全绿。
   ⚠️ 纪律 5 之后同一状态改判 denied 了,而那**不是**退回老坑:解锁与建行现在
   发生在同一处(`get_or_create_benefits`),"有权限但行还没建"从结构上不存在了。
   通则仍然成立:判权限前先分清"缺数据"与"无权限"。
4. **客户端前置闸只为省一次往返,判据必须与服务端同一套**。它是这道闸的**表达**,
   不是第二套规则 —— 抄一份就会抄歪:前端曾把「还没认领」判成「没有权限」,
   于是请求根本发不出去,服务端准备好的 `claimable` 永远等不到人。
   前端那侧同一个判断出现在多处时(拦截/自动播/UI 标),**只能有一个实现**;
   各写各的会出现"自动播说可以、拦截说不行",两边的单测还都是绿的。
5. **发权益前先扣费,不能反过来**(2026-09-19)。`/audio/unlock` 若先写解锁清单再扣额度,
   额度为 0 那次就是**权益已发、费没扣** —— 而这条路径正是免费用户撞墙后走的,
   白送的正好是我们要卖的东西。同理:扣费成功后解锁失败宁可重试,也别把顺序倒过来。
   配套:**花额度这件事必须用户显式确认**(同 `/activate`)。静默扣掉一次,用户在
   一件无所谓的作品上花完、走到真正想听的那件前才发现 —— 这是差评来源。
6. **权益判据别挂在会被别的功能清空的数据上**(2026-09-19)。"免费语音跟着识别走"
   最自然的实现是查 `recognition_events`(那张表已有 user_id + qid),但
   **删足迹 = 把该表的 user_id 清成 NULL** —— 用户一做隐私操作就连带没收了
   已经花额度换来的权益。因此解锁清单另存 `user_benefits.free_audio_qids`。
   ⚠️ JSON 列**原地 append 不会被 SQLAlchemy 标脏**,更新会被静默丢掉;整列重新赋值。
7. **范围票上线后,每一处"持票就放行"的读取都必须带上"这是哪家馆"**(2026-09-28)。
   只有音频端点按城市判时,其余几处是范围盲的:`/me` 对持巴黎票者在荷兰的馆说"生效中"(本地闸放行、点播放 402)、
   `/activate` 可能烧掉另一国的未激活票、`/audio/unlock` 幂等返回却什么都没解锁(卡死)、识别持任意票就不限次。
   → 判断依据是**资源所属的馆**(qid 反查),不是请求带的 slug;新增按票放行的路径先问"它知道是哪家馆吗"。
   🔑 **别用"判断发生在知道上下文之前"当范围盲的理由**:我初稿说"识别在知道馆之前发生,没法按馆判",
   但计费本来就在**命中之后**才扣 —— 先查代码里计费实际在哪一步,再下结论(用户纠正,D7)。
8. **未知商品不覆盖任何馆;"在售"不等于"可见"**。`pass_scope` 曾对未知商品默认 `paris` —— 新国家漏配就静默变成巴黎票。
   宁可锁住,不可错放。下发给前端的可买票(`offers`)与卖点馆名(`covers`)**只列覆盖已放出馆的**:
   演练期把新国家的票设为在售,公众也拿不到(只有预览账号)。
9. **派生权益必须有期限,且整个系统只有一种期限**(D8)。持票期间识别会把作品写进"永久免费可听",
   等于票过期后仍能听 —— 一张派生的永久权益绕过了付费边界。收紧后音频权利只剩「7 天」一个边界,
   用户能理解、代码无特例;持票识别不再写免费清单。

**身份**:`user_id` **一律取自令牌**,永不取自请求体/查询参数(此类 bug 犯过两次:
读别人权益、烧别人的票;以及权益 user_id 存成设备号导致付了钱看不到票)。
注册/Google 登录必须让游客**就地转正**(同 UUID),新建行会让已购通票凭空消失,
且恢复购买救不回(收据幂等返回旧记录、不给新用户发权益)。

## 搜索（打字查找;✅2026-07-13;稳定契约+可替换引擎）

识别的姊妹功能。**2026-10-11 方案 B 起无图件不返回**(含编号精确命中;用户看不到图就无法确认是不是眼前这件),与浏览列表同口径 `has_image_clause`;补图后随索引重建 ≤600s 自动出现。**打字搜索 ≠ 识别匹配**:识别是整串模糊相似(GPT/向量给完整候选),搜索是子串/前缀/分词命中(用户打"梵高"/"moulin"/"RF1668");搜索匹配独立设计,仅复用 matcher 归一化工具。

**两端点(加法,响应同族)**:
- `GET /api/v1/search?q=&language=&limit=20`——全局(探索页),响应含 `museums`+`objects` 两段。
- `GET /api/v1/museums/{slug}/search?q=&language=&limit=20`——馆域(馆列表页),只有 `objects`;馆不存在 404。

响应:`{query, museums:[{slug,name,city}](仅全局), objects:[{qid,title,artist,year,thumbnail,museum,has_image}]}`。`title/artist` 走既有显示名规则(`_resolve_name`,全语种);~~无图 stub 照常在 `objects`~~(2026-10-11 起不返回;`has_image` 恒为 true,只有 view 图的件 `thumbnail:null`);`museum`=归属馆 slug(点击跳讲解页,与识别 match 同款导航);空 `q`/无结果 → 诚实空态 `objects:[]`。全语种搜(藏品 `title_i18n`+作者 `name_i18n` 全语种进索引,中文界面打 Van Gogh 也中)。

**稳定契约 + 可替换引擎**(照搬识别架构):用户可感知行为由契约锁定、跨引擎不变;引擎可插拔。**首发=进程内索引**(`search/inprocess.py`,单一真相源=Postgres、零同步,馆域索引 TTL 600s 缓存;三路匹配:编号精确 1.0>纯数字按馆藏号数字 0.9>编号前缀 0.85(输入须同时含字母和数字,「RF1984」出 RF 1984 164;只输「RF」或纯数字不做,10-19)>标题前缀 0.8>标题子串 0.6>作者子串 0.4,同分按 popularity)。**规模触发换引擎**(藏品越过 ~5-10 万件/卢浮+蓬皮杜级别,或实测延迟退化)→ 自托管 Meilisearch/Typesense(CJK 分词好、百万级即时);换引擎只换 `search()` 实现,**契约与前端零改**,唯排序权重可微差、"能搜到什么"一致。

**识别未收录→搜索闭环**:相机识别兜底的「展签检索」sheet 即全局即时搜索,命中点选→讲解页(识别与搜索兜底互通)。

## 用户反馈（内容质量的兜底环;✅2026-09-18 #578/#579）

> 📎 设计与取舍见 [`../superpowers/specs/2026-09-18-user-feedback-design.md`](../superpowers/specs/2026-09-18-user-feedback-design.md)。

**为什么它属于契约而不是一个杂项端点**:CLAUDE.md 的 AI 内容质量原则写着「人只审形式安全、
不审事实对错,**错漏靠用户反馈兜底**」。生成侧的闸(接地/忠实度/语言一致性/锐度/响度)全建了,
这是**消费侧唯一的入口** —— 没有它,那条原则的后半句没有实现。

**加法端点**:`POST /api/v1/feedback` → **204 无响应体**(成功什么都不返回)。

**一条管道吃两类反馈,靠 `scope` 分**(不拆两个端点:共享几乎全部字段、同表、同护栏):

| `scope` | 含义 | 必填 | `kind` 取值 |
|---|---|---|---|
| `object` | 某件藏品的内容/音频有问题 | `museum_slug` + `qid` + `language` | `content_wrong` `audio_bad` `audio_missing` `other` |
| `app` | App 整体意见 | 无坐标 | `app_crash` `recognition_bad` `feature_request` `other` |

其余字段全可选:`text`(≤1000)、`device_id`、`app_version`、`platform`。
**`scope=object` 缺任一坐标 → 422 拒收**:没坐标的藏品级反馈是垃圾数据,存下来也定位不到行。

**🔴 `language` 必须传 API 语言参数,不是 UI locale**(繁体是 `zh-hant` 不是 `zh`)。
10 语 = 10 份独立内容(独立生成/翻译/音频),带错语种 = 让人去修错的那一行。

**匿名可写**(Bearer 可选):最需要反馈的时刻往往正是游客态,要求登录等于把它挡在门外。
带了令牌就认人;**令牌过期/无效不报错,当匿名收下** —— 不能让用户填好的文本因为令牌过期白丢。
`user_id` 一律**由后端从令牌取**,前端不传、传了也不信(与付费墙同一条纪律)。

**`kind` 是用户能感知到的现象,不是技术分层。** 绝不让用户选「文本问题 vs 音频问题」:
他不懂这个分层,而且会选错 —— 繁体念错那次文本是对的、TTS 念错了,用户只会说"读得很怪"。

**去重在读侧,不在写侧**(`scripts/feedback_report.py` 按不同 `device_id` 计数)。
双击提交/超时重试会造重复行,但"第三个人报同一件事就浮上来"这个排序数的是**多少人报过**,
不是多少行;写侧加幂等键更贵且更不准。

**限流 60/hour**(不是 `guest_login` 那种 5/hour):博物馆共享 WiFi 下同出口 IP 多人反馈是真实场景,
而这个端点写坏了最坏后果是垃圾行(SQL 能批量清),不是账号/资金风险。
⚠️ 按 IP 限流要**真实客户端 IP** 才有意义,见 `app/main.py` 的 `TRUSTED_PROXY_HOSTS`(#577 之前全站共享一个桶)。

**⚠️ 自由文本 = 个人数据**:`text` 是用户手写内容,上线前隐私政策必须有对应披露段。
凡加「用户能自由输入」的字段,连带三件事一起做:**政策披露 / 删号断链 / 数据导出包含**。

## 公开网站(网站 v1;2026-10-22,spec `2026-10-22-website-v1-design.md`)

后端直接出 HTML:`/{lang}/`、`/{lang}/{city}/`、`/{lang}/{city}/{museum}/`、`…/artists/{qid}/`、`/{lang}/{city}/{museum}/{qid}/`,
外加 `/sitemap.xml`、`/sitemap-{lang}.xml`、`/robots.txt`、`/w/static/*`、`/w/audio/*`、`POST /w/e`。代码:`app/api/web/site_pages.py` + `app/services/website/`。
与 App 契约(`/api/v1/*`)无关,零改动。

1. **网页层不带身份、不点火**:只读已发布内容,不调内容接口路由、不调懒生成/TTS。「有内容」= 该**请求语言**有已发布非空 guide 且有可展示图。
2. **可见性同 App**:只认 `published_at IS NOT NULL` 的馆;隐身馆在页面、搜索、作者页、sitemap 里都不出现。新路由带 slug/qid 参数要登记 `test_visibility_routes.py`。
3. **音频只给试听件**:每馆每语言自动 ≤5 件(`website/trials.py`:必看清单内、该语言导览有音频、各段音频最全优先;无清单按同分规则),经 `/w/audio` 302 到 1 小时 R2 预签名地址;其余作品页面里不出现任何音频地址。
4. **必看清单与官网地址在 `museums.yaml`**(`must_see:`、`website:`),上新馆一并填;没填必看清单的馆不出「必看」区。
5. **薄页**:馆/城市页某语言 <20 件、作者页 <3 件 → `noindex`,不进 sitemap / hreflang(页面照样能开)。无名作者卡不出作者页、不显示 qid。
6. **统计自记**:`web_page_view`(lang/page_type/device/internal_ref/bot)+ 信标白名单 `web_download_click|web_trial_play|web_trial_complete|web_share_click`;不设 cookie、不用本地存储。每次访问看几页 = `web_page_view` 数 / `internal_ref=false` 数(近似值)。`recognition_succeeded` 自 2026-10-22 起带 `qid`。
7. **上线开关**:`SHARE_PLAY_LIVE`(Play 链接)与 `WEBSITE_LIVE`(旧 `/a/` 链接 301 到新作品页)。`WEBSITE_LIVE` 必须在宿主机 nginx 把 `/{lang}/` 反代到后端之后才开(`deployment/production/nginx-gomuseum.app.website.conf`);`share.page_url()` 仍发 `/a/` 链接。
8. **`site_pages` router 必须最后挂到 app 上**:`/{lang}/{city}/` 会吞掉之后注册的两段路径(如 `/api/health/`)。
