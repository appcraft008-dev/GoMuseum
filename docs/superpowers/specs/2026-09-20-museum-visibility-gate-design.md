# 上新馆可见性闸（准备期隐身 · 一次放出 · 正式包预览）

> 2026-09-20 brainstorm 定稿。⏳ **待并入**：同日跑的独立 review 尚未回来，
> 其发现回来后折进本文再实施（见 §七）。
> 与 [[enrichment-pipeline-v1]]、[[collection-coverage-strategy]] 配套——
> 那些管"怎么把一家馆灌出来"，这个管"灌到一半时用户不该看见它"。

## 为什么要做

**理由一：prod 上不存在「未完成」这个状态。** 上一家馆（目录 → 文本生成 →
翻译 → 音频灌入 → 通票商品）要几周，而这几周的工作**全部在 prod 上进行**。
一家馆 `INSERT` 进 `museums` 表的那一瞬间，它同时从四个口子对所有真实用户可见
（见 §二）。目前唯一的"保护"是**还没有真实用户**——Play 一放量这条就失效。

**理由二：staging 结构上就不是暂存区。** `scripts/sync_staging_from_prod.py:2`
第一行写着 `prod → staging 内容表搬运`，方向是单向下游。就算反过来用也过不去
两道墙：①「生成一次、永久落库」——在 staging 生成再在 prod 重生成 = LLM+TTS
付两遍钱，一家卢浮宫量级 $40 起步，含音频更多；②音频在 R2，staging/prod
不同桶，搬内容表容易，搬音频对象 + 重写 `audio_key` 是另一套迁移——而 R2 那边
`--grace-days` 护栏已经因为一次批量 mtime 重写失效过（[[r2-orphan-audio-gc]]）。

**理由三：数据齐 ≠ 界面对，而现有验收只验前者。** `scripts/onboard_verify.py:31`
自述 `只读,不改数据`，九项全在查 DB 列。这个项目最贵的几个坑恰恰都是"数据在库里、
App 上不对"：富化把 `title_zh` 变 null 崩掉整个馆藏页（[[enrichment-data-frontend-contract]]）、
`category_sections` 缺映射让 980 段/2800 件"从看不见变看得见"、小皇宫展签空白。
**没有一个是数据计数能抓到的。**

> ⚠️ 期望值：本功能**不产生任何用户可见的新能力**。它的价值全在"出事时没出事"。
> 判断标准不是"好不好用"，是"上新馆时真实用户有没有看到半成品"。
> 所以——**最省形态就是对的形态**。

## 原则

### 1. 可见性是馆的属性，不是内容的属性

判据统一在**馆**这一层，不下沉到藏品/段落。一家馆在用户心智里是一个单位：
"巴黎有五家，其中两家点进去是哑的"比"巴黎有三家"差。半开的馆比不存在的馆更伤。

推论：不做"按藏品灰度放出"，不做"按语言分批放出馆"。放出 = 整馆一次翻开关。

### 2. 用时间戳当开关，不用 bool

```
Museum.published_at  DateTime NULL    # NULL = 准备中，不可见
```

**既是开关又是记录**：上线日期不必另找地方记。bool 只能回答"在不在线"，
时间戳还能回答"什么时候上的"——而后者是排查"某天指标跳变"时的第一个问题。

### 3. 预览特权与付费权益正交

```
User.can_preview  Boolean default false
```

`can_preview` **只回答一件事**：这个调用者能不能看到 `published_at IS NULL` 的馆。
它不发通票、不给识别额度、不碰任何别的东西。

这条正交性是多账号验收方案成立的**前提**：

| 账号 | can_preview | 通票 | 验什么 |
|---|---|---|---|
| **A 内容号** | ✅ | 有 | 数据完整性、渲染、音频能播、搜索命中、拍照识别、切语言 |
| **B 付费号** | ✅ | **无** | 撞付费墙、价格显示、购买→发票→验证→发通票→激活全链路、免费额度 |

B 号当**消耗品**用：免费识别 5 次按账号算，验一次配额就耗尽。所以
`can_preview` 必须是 **DB 列而非环境变量**——开一个新号一条 SQL，不用重新部署。
（B 号记得进 Play 许可测试员名单，否则测购买要真付钱。）

### 4. 验收必须用线上那个 APK

本来可以用 staging flavor 打预览包（包名 `com.gomuseum.app.staging`，能与正式版
共存）。**否决**：那样验的是**另一个二进制**，而要抓的恰恰是渲染层的坑——验错了对象。

账号级预览让作者用**一模一样的正式 APK**走完整流程。这是选账号级而非
header/密钥方案的决定性理由，不是顺带的好处。

### 5. 放出是 server-driven 的一条 SQL

```sql
UPDATE museums SET published_at = now() WHERE slug = '...';
```

不发包、不过审，符合契约「能用改后端免 Play 审核解决的，不靠发新 App 版本」。
⛔ prod 写操作由用户执行。

## 二、暴露面清单（改动点）

一家馆 `INSERT` 后当前立即可见的四个口子：

| # | 口子 | 位置 | 现状 |
|---|---|---|---|
| 1 | 探索页馆列表 | `museum_repo.py:354` `list_museums` | 查全表，**零过滤**；端点无 auth |
| 2 | 拍照识别 | `matcher.py:48` `build_index(museum_id=None)` | 全局索引 |
| 3 | 搜索藏品 | `inprocess.py:140` `build_search_index` | 自述「单一全局索引」 |
| 4 | 搜索馆 | `inprocess.py:189` `_search_museums` | 馆本身也在全局搜索里 |

（第五个在路上：[[product-backlog]] 里冻结待命的公开网页层
`gomuseum.app/a/{slug}/{qid}`，实现时必须一并带上本闸。）

⏳ **本清单待 review 补全**——"我能想到的入口"不等于"全部入口"，
`get_museum_pack` / content / 分页 objects / 足迹 / KPI 等仍需逐个核。

过滤条件统一成：

```
published_at IS NOT NULL  OR  调用者.can_preview
```

`list_museums` 目前完全没有 auth，需加 optional bearer 才能知道调用者是谁。

## 三、已知缺口：游客态无法预览

游客没有账号 → 没有 `can_preview` → 看不见隐藏的馆。

**判定可接受**，理由是游客的坑是 **App 级而非馆级**：真机抓到的那三个入口
（路由守卫把游客当已登录、push 到 shell 路由黑屏、收据冲突逃生口，见
[[product-backlog]] #485/#486）都与是哪家馆无关；付费墙本身在音频端点上按
`credentials` 判，对游客一律 402，同样与馆无关。**游客流程在已上线的馆上验就够了。**

真正与馆绑定的只有一件：新国家若要建**新的通票商品**（如"罗马通票"），
该商品的购买链路是全新的，必须验——那需要真账号，正是 B 号的活。

## 四、安全边界

预览特权的爆炸半径：**只放大"能看见几家馆"这一件事的读可见性**。
不给写权限、碰不到他人数据、不发任何权益。忘了关，后果仅是该账号多看见几家未上线的馆。

## 五、前向兼容

后端单侧改动，契约**形状零变化**，老 App 只是收到更短的馆列表。
⏳ 待 review 确认的反向风险：某馆**曾可见后又不可见**时（回收、或预览账号取消特权），
足迹里已有该馆记录、已缓存的 slug、深链接会不会崩。
同类事故有先例（`title_zh` 变 null 崩整页），不能想当然。

## 六、自检

按 [[test-across-config-dimension]]：行为依赖"某项配置在不在"时，测试必须在配置
**两侧**做同一组比较。只测"预览者看得到"等于只测一半，而且它会绿。

**2×2 必做**：

| | 已发布馆 | 未发布馆 |
|---|---|---|
| **普通调用者** | 看得到 | **看不到** |
| **预览调用者** | 看得到 | 看得到 |

四个暴露面各跑一遍这张表。

## 验收口径（上新馆配方补充）

放出前两道门：

1. **数据层**：`onboard_verify` 九项全绿（前置条件，保留）
2. **渲染层**：作者用正式 APK 登录 A 号走探索→藏品详情→播音频→搜索→拍照识别→切语言；
   再用 B 号（无通票）走付费墙与购买链路

翻开关的第三个前置条件：**该馆对应的通票商品在 Play 侧已生效**。
否则用户看得到内容、撞到付费墙、**买不了票**——比看不到馆糟糕得多，
且同类丢钱洞已经出过一次（[[product-backlog]] #485）。
