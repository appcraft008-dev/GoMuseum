# 分享与公开网页层设计（一套页面、两个渠道、分开判生死）

> 2026-09-20 brainstorm 定稿。起点是"把正在看的藏品分享给朋友"，
> 落点是**公开可读可听的网页层** —— 它同时是分享的载体和 SEO 资产。
> 与 [[monetization-plan]]（付费墙）、[[audio-guide-positioning-and-paywall]]（定位）
> 配套：那两个管墙内，这个管墙外唯一的门面。

2026-09-20 用另一模型独立复核过（按 CLAUDE.md 第 6 条：**复核的是推理的原始材料，
不是结论** —— 给的是事实清单 + 四个前提质疑题，先不给方案，避免只拿到"写得不错"）。

## 为什么形态是"网页"而不是"分享按钮"

**理由一：分享是放大器，现在没有东西可放大。** 真实用户 0，App 还在内测轨道没放量。
0 × 任何 K 因子还是 0。所以这个功能的价值不在"老用户拉新用户"，而在
**给还不存在的第一批用户造一个入口** —— 按获客渠道设计，不是按病毒循环设计。
这个重新定义改掉了后面每一个选择。

**理由二：落在应用商店的分享链接必然漏光。** 朋友点开 → 商店 → 装 → 注册 → 才看到内容，
四步漏斗每步掉 60-80%；而且朋友大概率不在巴黎，对"巴黎导览 App"零需求。
落在**能立刻读能立刻听的网页**上，朋友零摩擦就消费到了内容，
愿意装的才是真要去巴黎的人。

**理由三（⚠️ 已被 2026-09-20 复核大幅削弱，原文说"量级很可能大过分享本身"）：
同一套页面顺手是 SEO 资产，而这条渠道不依赖先有用户。**
665 件有正文讲解 × 多语言 = 几千个可索引页面。

> 🔴 **但这条不该再当作方案的主要理由。** 复核指出的是结构性问题，不是"对手比我们大"：
>
> - **高量词**（"蒙娜丽莎"）：维基百科、卢浮宫官网、Google Arts & Culture
>   的域名权重高出几个数量级，新域名在任何现实时间窗口内都排不进首页。
> - **长尾词**（小皇宫某冷门画家某件作品）：竞争是小了，**但搜索量同样趋近于零** ——
>   会想查这件作品的人，几乎全部是**此刻正站在它面前**的人。
>   而那批人恰恰就是 App 要覆盖的对象。**现场识别是 App 存在的理由，
>   这个理由不会在人离开博物馆之后变成搜索行为重新出现。**
>
> 我认为还剩一点未被驳倒的价值：我们的内容是 **10 语**的，
> 而维基百科在小语种上的藏品覆盖远不如英法 —— 长尾 × 小语种的竞争确实弱得多。
> 但这块我们自己的内容量也最薄（非英法中语种普遍个位数，见 [[six-languages-rollout]]），
> 所以它现在撑不起一条渠道，只能算"以后可能有"。
>
> **结论：SEO 降级为副产品，不是做这件事的理由。** 方案的理由收回到
> 理由一、二（分享落地）+ 下方「不需要指标证明的价值」（门面）。

> ⚠️ 期望值：零用户期间**分享那条路的数据恒为 0，这不是失败信号，是没有输入**。
> 见下方「分开判生死」。

## 原则

### 1. 分享落地 = 可读可听的网页，App 入口不抢戏

`gomuseum.app/a/{slug}/{qid}` —— 作品图 + 完整文字讲解 + guide 音频播放键。

**文字全给，不只给 guide。** 文字本来就公开（`GET /museums/{slug}/objects/{qid}/content`
无鉴权，谁调 API 都拿得到），藏着没意义；SEO 要的正是内容厚度。
App 的价值是**在现场拍一张就认出它**（识别），不是独家文字。

```
┌─────────────────────────┐
│  作品图（large）          │  ← OG 卡片用的也是这张
├─────────────────────────┤
│  《门闩》 弗拉戈纳尔 1777  │
│  ▶ 听讲解  3:12          │  ← 签名 URL，只有 guide
├─────────────────────────┤
│  guide 正文              │
│  深度模块（文字，平铺）     │  ← tabs 里剩下的
│  常见问题                 │  ← suggested，顺便吃 FAQ 结构化数据
│  作者卡                   │
├─────────────────────────┤
│  [粘底条] 在博物馆现场，    │  ← 随时可点，不挡内容
│   拍一张就能认出它 →       │
│  图片来源 / 内容来源声明    │  ← images.credit 字段已有
└─────────────────────────┘
```

### 2. 🔴 音频开口：只给 guide，且绝不下发直链

网页访客（无 App、无账号）可听 **guide 一段**。深度模块 / 问答 / 作者介绍
**全部不给** —— 那些是"用起来"才需要的，正好留在墙内。

理由：卖的是"整场参观不限次用"，不是某一段音频。听一段 3 分钟讲解不会让人不买通票，
**反而是唯一能让陌生人知道我们好在哪的方式**。天然限量：guide 段有音频的只有
131 件（2026-09-20 实查 prod）。

> 🔴 **2026-09-20 复核推翻了本条原来的一半论据。** 原文写「App 里免费用户本来就有
> 试听额度（`free_audio_qids`），网页免费听不比它更松」—— 这是错的。
> `unlock_free_audio` 的全部三个调用点（`entitlements.py:122`、
> `recognize_global.py:145`、`recognition/service.py:368`）**都要求 user_id**，
> 即：登录 + 花掉一次识别配额 / 走带闸的 unlock 端点。
> 网页匿名听**没有任何等价门槛**——不需要登录、不需要配额、不需要人在现场。
> 这不是"一样松"，是**结构性地更松，是一个全新的免费层**。
>
> 因此本条降级为**待决策**，不是已定方案。真要给，保守形态是**试听片段**
> （前 30-60 秒）而非完整 guide —— 把完整开放的决定留到有真实流量、
> 能真正验证"伤不伤转化"的那天。零用户期做不了这个验证（没有转化可伤害），
> 而验证不了 ≠ 没风险。

**🔴 实现硬约束**：SSR 服务端自己查 DB 拿 `audio_key`，页面上给**短期签名 URL**。
绝不复用内容接口下发直链 —— `museum_repo.py:566` 已有这条纪律：

```
# ⚠️ 只给标志位,**绝不下发直链**:内容接口无鉴权,发直链等于
# 把付费墙拆了(音频 key 做成不可推测也白搭——我们自己发出去)。
```

实现时很容易顺手复用现成的内容接口，一下就把墙拆了。配套要限流 + 异常量监控。

### 3. 🔴🔴 新路由绝不能走 `maybe_trigger` —— 否则爬虫直接点燃 LLM 账单

**这是本方案第一天就存在的最贵敞口，2026-09-20 复核发现（原稿完全没看到）。**

`object_content` 端点在返回内容前**无条件**调用
`maybe_trigger(db, qid, schedule=..., language=language)`（`museums.py:82`）。
该函数（`enrichment/lazy.py:233`）有三条会花钱的路径：

| 条件 | 触发 | 有锁吗 |
|---|---|---|
| 缺图 | `run_lazy_images` | ❌ **连锁都不拿** |
| `content_status == "stub"` | `run_lazy_generation`（完整 LLM 生成） | per-qid 锁 |
| `ready` 但请求语言无内容 + 有 en 轴心 | `run_lazy_translation` | per-qid 锁 |

那把锁只防"同一 qid 被重复触发"，**完全不限制不同 qid 被逐个触发的总量**。
而全局速率限制也不存在：`core/rate_limit.py` 的 `Limiter(...)` **没设
`default_limits`**，`museums.py` 的 content 路由上也**没有 `@limiter.limit`**。

于是：公开路由 `/a/{slug}/{qid}` 一上线，Google/Bing 爬虫顺着站内任何链接
走到未发布的件上（qid 是公开的 Wikidata 标识符，**本身就可枚举**），
每一次访问都点燃一笔真金白银 —— 覆盖面是 27221 − 665 ≈ **26500 多件**里
状态为 `stub` 的那部分。

**🔴 而且语言维度会把它乘一遍。** 本文档原则 8 写着"链接带 `?lang=`，页面上可切换"
—— 语言切换正好命中上表第三行（懒翻译）。665 件 × 10 语 = **6650 次翻译任务**，
一个爬虫（或一个好奇的用户）把语言挨个点一遍就够了。

**附带的更深伤害**：这会绕开项目一直守的"每批 10 件、人工验质量"的生成纪律
（见 [[petit-palais-batch-generation]]）—— 变成由**爬虫的访问顺序**决定下一批生成谁，
与「正确性靠构造不靠人审」直接冲突。

**修法（必须写进实现，不是二期）**：新路由**自己查 DB**，
`content_status != "ready"` 一律返回静态 404 + `noindex`，
**绝不经过 `maybe_trigger`**。即：不要因为"内容接口反正是公开的"就复用它 ——
那个端点的公开性和它的副作用是两件事，而本文档原则 1 恰恰是用前者论证的。

### 4. 网页层住在 FastAPI（服务端渲染）

| 方案 | SEO | 代价 |
|---|---|---|
| **FastAPI 出 HTML**（选） | ✅ 天然 SSR | 一个路由 + 一个 Jinja 模板 |
| 构建时预渲染静态页 | ✅ 最好 | 一套构建管线，**内容一变就得重建** |
| 现有 nginx + 前端 JS 拉 API | ❌ 基本拿不到 | 最快，但砍掉方案一半的价值 |

决定性理由：我们的内容**一直在变**（懒生成、补翻译、重生成都在跑）。预渲染每次内容更新
都要重跑构建，这个运维负担远大于它省下的运行时开销 —— prod 本来就在跑 FastAPI。
抗爬和缓存交给 nginx 加一层 cache。

### 5. App Links ≠ 下载入口（两件不相干的事）

**App Links** 是不可见机制：让**已装用户**点 https 链接时系统直接开 App 而非浏览器。
要在 `gomuseum.app` 放 `assetlinks.json` 并配签名指纹，需一次真机验证。
它对没装 App 的人**完全不起作用**。

**下载入口**是网页上的按钮，解决的是未装用户。两者分开做。

### 6. 下载 CTA：按设备分，粘底条，文案说好处

分享链接 99% 在手机浏览器打开 —— 人已经在手机上，给二维码等于让他扫自己屏幕。
二维码只对**桌面访客**有价值（SEO 来的人很多在电脑上搜）。

| 访客 | 给什么 |
|---|---|
| Android 手机 | 按钮 → Play Store |
| iPhone | 按钮 → App Store（**目前只有 Android 包，这里要给诚实提示**） |
| 桌面 | **二维码** + "用手机扫码下载" |

一个按钮，JS 判断 UA 决定去哪。

**不要用 logo，logo 不传达任何理由**：
- ❌ `[GoMuseum logo] 下载`
- ✅ `在博物馆现场，拍一张就能认出它 →`

后者正好是我们唯一不能在网页上给的能力。

**位置是粘底条，不是第一屏顶部。** 朋友点开分享看到的第一眼如果是推销，
页面就失去了"有用的东西"这个属性 —— 而这正是他愿意点开的唯一原因。
真正会下载的是读完听完觉得好的人，那时他低头就看见它。

### 7. 第一版只做单件作品，不做足迹分享

足迹分享社交价值更高（是"我的"不是"它的"），但现在做不了：
**零用户 = 零足迹，没有素材**。且足迹是私人记录，公开要单独处理隐私，
还拿不到 SEO（私人页面不可索引）。

单件页做完后，足迹页本质上就是"把 N 张单件卡片拼起来"，增量很小。
等有真实用户再做。

### 8. 分享入口只在有内容的件上出现

27221 件里只有 665 件有正文讲解。用户在卢浮宫随手拍一件小众展品大概率是"待完善"。
**分享一个空页面 = 负向拉新**，朋友的第一印象是"这 App 没内容"。

落地做法：App 讲解页右上角系统分享图标（`share_plus`，当前**未引入**，要加），
**仅在 `tabs` 非空时渲染**。链接带 `?lang=`，跟分享者当前语言；页面上可切换。

### 9. 🔴 链接必须带来源参数，否则这功能永远无法被评价

链接尾部带 `?s=app`（App 分享）/ 无参数（搜索来的）。

不加这个，我们只会看到"网页有流量"，分不清是分享还是 SEO 的功劳 ——
**而这两条路的优化方向完全相反**，混在一起等于白做。

## OG 卡片（微信 / WhatsApp 里那张预览图）

这张图决定点击率，比页面本身更重要 —— 绝大多数人只看到它。

- `og:image` = 作品图
- `og:title` = 《门闩》— 弗拉戈纳尔
- `og:description` = guide 正文前 ~100 字

**🔴 不要放 logo、不要出现"下载"字样。** 卡片要看起来像一件艺术品，不像一条广告。
朋友在群里看到的应该是"哦这画有意思"，不是"又在推 App"。

## 怎么知道这功能有没有用

### 三个不能当判据的虚荣指标

- ❌ **页面 PV** —— 什么都不说明
- ❌ **分享次数** —— 分享了没人点等于 0
- ❌ **下载量** —— 装了不打开等于 0

唯一算数的是：**通过这条路进来、最终完成一次识别的人**。
识别是核心动作，没做过识别的安装量是噪声。

### 🔴 两条路分开判生死

**SEO 那条不依赖用户，现在就能判。** 判据：上线 **3 个月**后看 Search Console 的
索引量和自然点击 —— 索引了但点击接近 0，说明这批内容没人搜，停止扩大
（已建页面留着，零维护成本，不必删）。

> ⚠️ 复核修正："不依赖用户"≠"免费"。这条路押的是**三个月的域名声誉**，
> 一旦站点级质量信号被触发，会连累本来内容扎实的那 665 件。
> 所以别把它当成"反正不依赖用户，先做着"的理由。
> **验证形态应该缩到最小**：先发布十几个代表页、提交 sitemap，
> 观察一个月，而不是一次性建完整路由去服务几百个 qid。

**分享那条完全依赖有真实用户在用。** 建议等到 **≥100 个真实活跃用户**之后再看它的数，
在那之前看了只会得出错误结论。

混在一起看是最糟的：会把"没有用户"误读成"分享功能没用"，
然后砍掉一个从没被真正测试过的东西。
（同类错误见 [[proxy-metric-is-not-the-thing-you-ship]]。）

### 第一版的漏斗会断一截

能测到：点开链接 → 读完/听完 → 点下载按钮。

**测不到**：点下载 → 真的装了 → 真的用了。网页访客没有 user_id，
要靠 Install Referrer 才能把安装接回那次点击 —— 那是二期。

部分补救：Play Console 自有安装来源数据（UTM），能看到"从网页来的安装数"，
只是接不到具体哪一次分享。

### 一个不需要任何指标证明的价值

分享页本身就是**这个 App 唯一能给人看的门面**。朋友问"你在做什么"、
找博物馆或旅行社谈合作、甚至 Play 审核，都需要一个不用装 App 就能打开的东西。
这部分做完就有，不依赖转化率。

## 失败模式与对策

| 风险 | 对策 |
|---|---|
| Google 不索引（新域名 + 规模化 AI 内容容易被降权） | **分批上线，只上 665 件有真内容的**，绝不放出"待完善"页 |
| 音频被爬 | 签名 URL + 限流 + 异常量监控 |
| **内测轨道没推正式** | **前置条件，不是并行项**（见下） |
| 分享页是"待完善" | `tabs` 非空才给分享入口（原则 8） |
| 公开发布暴露归属问题 | 页脚来源声明；`images.credit` 字段已有 |

### ⚠️ 硬前置条件

**App 目前在内测轨道，Play 链接对外人打不开** —— 分享页上的下载按钮今天点下去是
"找不到该应用"。本功能上线**必须排在"推到正式轨道"之后**，
否则每一个被拉来的人都撞在一堵墙上。

这回到 [[product-backlog]] 里一直没做的那件事：发版最后一步（内测 → 正式放量）
是这个功能的前置条件。

## 二期（不在第一版）

1. **Install Referrer 回流**：分享链接带参数 → Play Store → 装完 App 读 referrer →
   **直接打开那件作品的讲解页**。现在的流程是装完打开是空白首页，刚才那件作品没了，
   兴趣断在这儿。体验差异很大，但实现较重。
2. **足迹分享页**：等有真实用户（原则 7）。
3. **音频铺量**：分享页的"可听"目前只覆盖 131 件。
   音频铺法的 3 倍杠杆见 [[audio-guide-positioning-and-paywall]]。

## 已确认的现有基础设施
