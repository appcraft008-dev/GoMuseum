# 识别失败的找回、引导与照片反馈 · 设计

- 日期:2026-10-05
- 状态:待用户审阅
- 来源:与用户的头脑风暴(本文「决策」一节逐条对应讨论中的共识编号)

## 一、要解决的问题

用户最初的问题:**我们永远不知道用户认不出的是哪些作品,也就无法改进**;能否让用户上传认不出的照片,又不违反隐私政策。

讨论中扩展为三件事:

1. 识别结果**丢了**(「识别失败」其实服务器算完了,只是没送到用户手里);
2. 认不准时用户**被困住**(候选点错回不去、「都不是」后只有拍说明牌一条路);
3. 认不出的信息**没回到我们手里**(「都不是」后端不知道、找到的正确答案被扔掉、照片不存)。

**成功标准**:每一次认不准,后端都留下一条可定位、可排序的记录;用户在任何分支都有一条通向正确答案的简单路径;正常「一次认出」路径不变慢。

## 三、决策(对应讨论共识编号)

**等待与「识别失败」**
- ① 识别结果不因切走 App 而丢失;切回来就像没离开过。实现=App 自动重发**同一张照片**。
- ⑪ 等待分段提示;约 20 秒后显示「可以先切到其他应用,回来时结果还在」。只承诺切 App,不承诺离开页面。
- ⑫ 先给后端识别加分步计时,用真实数据找出慢在哪里再优化。
- 硬性要求(第 4 点):**同一张照片的在途请求必须合并**,否则重发会让等待变长、AI 调用翻倍。

**候选**
- ② 用户真正判断对错是在详情页看大图。
- ③ 候选图可直接放大;从详情页返回回到候选列表可换一件。不加新按钮。

**「都不是」/ 完全认不出**
- ⑤ 给选择页,不替用户决定。
- ④⑥ 两个并列主按钮:「拍说明牌」「输入编号/名称」(引导优先馆藏号,其次说明牌原文名称);「重新拍作品」为小字。
- ⑭ 编号搜索:整串精确优先;只输入数字且无精确结果 → 退一步按数字匹配,全部列出,每条显示完整编号+标题。

**向用户要照片**
- ⑦⑧ 弹确认(进详情页前)的时刻:①说明牌/编号**找到了** ②最终**没找到** ③从详情页返回后**换选了另一件**。
- ⑨ 选中排第 2、3 名的候选(选对了)不弹,只在后台记排名。
- 不勾不分叉:后续流程完全一样。
- ⑩ 弹框显示该照片缩略图、默认不勾;拒绝后本次打开 App 期间不再问;不加「不再询问」、不自动发送。补充文字选填。

**照片用途与隐私**
- ⑬ 照片只当信号不当资产,只做三件事:补录未收录作品 / 给无图作品找授权图并核对是不是同一件 / 诊断识别失败原因。**绝不**入识别库、**绝不**对外展示;最长 90 天、处理完即删(取先到);删号一并删。删后只留不含图像的数据(分数/答案/归因标签)。诊断集=最近 90 天滚动窗口。
- ⑮ 无图作品的详情页显示用户**自己刚拍的**照片:仅本机,不上传,不给他人用。
- ⑯ 找不到有授权图的作品,接受现状(靠说明牌/搜索)。
- 卢浮宫 3744 件「官网图链接」灰区:**维持现状不动**(用户 2026-10-05)。

## 四、方案:按子项目拆分

每个子项目独立可上线、各出一份实施计划。全部是**加法**契约,老版本 App 不受影响。

### S1 后端识别分步计时(纯后端,先做)

- `recognize()` 内按阶段记耗时:读图/校验 → 缓存查询 → 向量嵌入 → 向量检索 → 找画布/裁块 → GPT 读图 → 文字匹配 → 落事件;一行结构化日志带 `engine`、`outcome`、总耗时。
- 不改响应、不改 App。跑满约一周后出分位数报告(p50/p90/p99 按 engine),再定优化方向——本文不预设优化手段。

### S2 识别找回(后端合并在途 + 前端自动重发 + 分段提示)

- **后端**:以现有 `_cache_key` 为键加 Redis 在途锁。第二个同键请求不重算,等首个请求写缓存后读缓存返回(设上限,如 120s,与 nginx `proxy_read_timeout` 对齐);首个请求失败则释放锁、由等待者自己算。老 App 重试同图也受益。
- **前端**:
  - 请求未返回时 App 切回前台、或 60s 超时 → 用手里的同一张照片(`_captured`)自动重发一次;不弹「识别失败」除非重发也失败。
  - 分段提示(⑪):0s 现文案 → ~10s「比平时多花了点时间,还在找」→ ~20s「可以先切到其他应用,回来时结果还在」。
- 计费:重发命中缓存不扣(现状已保证),无需改计费逻辑。
- 已知遗留(不在本项目修):游客身份**重拍新照片**会被当新识别再扣一次。

### S3 候选交互

- 候选缩略图点击可放大(全屏看图,左右切换候选)。
- 候选 → 详情页由 `pushReplacement` 改为 `push`,返回回到候选列表(保留 `RecognitionCandidates` 状态)。
- 后端加法:`POST /recognize/confirm` 增加可选 `previous_qid`(改选时带上被替换的那件),落到事件上(新列,如 `rejected_qids` JSON)——「第一次选错」不再丢失。改选不重复扣(现状已保证)。
- 「都不是」上报:新端点 `POST /recognize/reject {phash, qids}` 落到同一事件,fire-and-forget。

### S4 选择页 + 编号搜索

- 「都不是」与「没认出来」共用一个选择页:「📷 拍说明牌」「⌨ 输入编号/名称」并列主按钮,「重新拍作品」小字。已有 `label_text` 时输入框预填。
- 输入框占位文案引导「馆藏编号(如 INV 779)或说明牌上的名称」。
- 后端 `rank()`:query 归一化后为纯数字、且无整串精确命中时,改按「馆藏号去字母后的数字串」相等匹配;结果显示完整编号+标题(无图作品也能对照说明牌区分)。
- 从选择页找到作品点进详情页 = 「这张照片 = 这件作品」:通过 S3 的 confirm(带 phash)回传,不传照片也能记下答案。

### S5 照片反馈(后端 + 隐私政策 + 前端)

**数据**:新表 `recognition_photo_feedbacks`(不复用 `feedbacks`:有图片、有分诊状态、有 90 天生命周期)

| 字段 | 说明 |
|---|---|
| id, created_at | |
| user_id / device_id | 同 `feedbacks` 惯例:令牌解析得出才填 user_id |
| phash, museum_slug, language, app_version, engine_model | 自动附带 |
| trigger | `found` / `not_found` / `corrected` |
| answer_qid | 找到/改选的作品(not_found 为空) |
| query_text, label_text | 用户输入/说明牌转写 |
| server_result | 当时的候选与分数(JSON) |
| text | 选填补充文字 |
| image_key | **私有**存储 key;删除后置空 |
| triage | `fixed_now` / `no_reference` / `real_failure`(自动分诊) |
| cause | 人工归因标签 |
| status | `new` → `triaged` → `done` |

- **存储**:独立私有桶(或 R2 私有前缀+无公开域名),**绝不**进 `gomuseum-assets` 公开桶、绝不写 `object_images`。
- **端点**:`POST /feedback/recognition-photo`(multipart,匿名可写,限流同 `/feedback`)。
- **生命周期**:每日任务删除 `created_at > 90 天` 或 `status=done` 的图片(置空 `image_key` 并删对象);删号删该用户全部图片;导出包含元数据(不含图片)。
- **自动分诊脚本**(`scripts/recognition_photo_report.py`,沿用 `feedback_report.py` 惯例不建后台):用当前引擎重跑每张图 → `fixed_now` 删图 / `no_reference`(答案作品无图)进补图队列 / `real_failure` 进诊断集;附线索(画布占比、过曝比例、模糊度);报告按线索分组列照片与答案参考图。
- **前端**:三个触发时刻(⑦⑧⑨)进详情页前弹确认框(缩略图+一句用途说明+可选文字,默认不勾);本次 App 进程内拒绝一次后不再弹(⑩);用户继续后照片在后台上传,失败静默重试一次,不阻塞。
- **隐私政策**(中英同改,**先于** S5 前端上线):照片「默认不存储;仅当你在反馈中主动发送时保存,用于补录作品、核对授权图、改进识别,最长 90 天,不对外展示,删号即删」。**Play 数据安全表单由用户在 Console 修改**(照片:可选收集)。

### S6 无图作品显示本机照片(纯前端)

- 识别命中/候选点选/搜索点选进入详情页时,若该作品无 hero 图,把 `_captured` 本地路径带入详情页,大图位显示「你拍摄的照片」。不上传、不缓存到他人可见处;离开详情页即不再显示。

### S7 补图数据任务(纯数据,无需照片)

- 41 件:Wikidata 新挂 P18 → 走现有 images 物化管线。
- 565 件(小皇宫):Wikidata P4765 指向 Paris Musées 图,P275=CC0 → 新增图源适配(只补缺不覆盖)。
- 766 件(小皇宫):有 Paris Musées 作品号(P6246)无图链接 → 用 Paris Musées API 逐件核实 CC0 图,先只统计不写入,报给用户再定。
- 走纪律 37:先列写入面(`object_images`/`object_embeddings`,只新增行),备份对应表,确认作废音频数=0。
- 排序:无图作品被「找到」的事件数(S3/S4 产生的 confirm 记录)从高到低。⚠️ 与讨论时「按设备数」说法的差异:`recognition_events` 按设计不存 device_id(匿名就是匿名),故按**事件数**计;每条事件=一次独立拍摄。

## 五、实施顺序与依赖

```
S1 计时 ──(数据)──▶ 之后的性能优化(另立项)
S2 后端合并 ─┐
S3/S4 后端加法 ┼─▶ 前端一版(S2 前端 + S3 + S4 + S6)── 搭下一班 App
S7 数据任务(独立,随时)
S5 后端 + 私有存储 ─▶ 隐私政策上线 ─▶ S5 前端(再下一班 App)─▶ 用户改 Play 表单
```

- 后端先行、前端后到(契约加法,老前端不受影响)。
- S5 前端必须晚于隐私政策上线。

## 六、测试要点

- S2:同键并发两请求只调用一次识别(计数断言);首请求异常时等待者自算;重发命中缓存不扣次。前端:模拟超时/切前台触发重发,只重发一次。
- S3:`push` 后返回仍是候选态;改选带 `previous_qid` 落库;reject 落库;改选不重复扣(已有测试保持绿)。
- S4:`779` 返回 4 件且含 `INV 779`;`INV 779` 只返回 1 件;字母数字混合不走数字退路。
- S5:匿名可写;图片只进私有存储(断言 key 前缀/桶);90 天与 done 清理;删号删图;导出不含图片;端点拒绝超大文件。前端:拒绝后同进程不再弹;不勾时流程与勾选一致。
- S6:无图作品显示本机照片,有图作品不受影响。
- 按记忆「跨配置维度测试」:S2 在 Redis 可用/不可用两侧都测。
