# 方案 A:懒生成防刷 设计

日期:2026-10-11 · 分支 `feature/lazy-gen-abuse-guard` · 状态:v2(已过 Fable 独立评审并按评审+prod 实测修订),待写实施计划
姊妹方案:[方案 B 无图作品不对用户开放](2026-10-11-hide-imageless-objects-design.md)(独立分支、在 A 之后做)

## 一、起因

10-10 #877 把懒生成全站日上限从 300 段提到 1000 段。用户问:这会不会让"爬虫雪崩"风险变高?

查证结论:
- **普通爬虫点不着**:内容端点只有带有效令牌才点火(`museums.py:139` `_caller_id`)。
- **脚本能点着**:游客令牌谁都能领;换 device_id 就是新游客号;`/guest` 限流 5 次/小时/IP → 单 IP 一天约 120 个号。
- **不会雪崩,但会变贵**:全站上限是硬顶,到线全站停到 UTC 零点。最坏一天约 $4–10、约 120 件冷门件永久入库;
  且一个脚本就能把当天额度吃光,让所有真实用户看到「明天再来」。
- 全站上限是钱包止损,不分是谁 —— 缺的是"按账号""按 IP"两道。

## 二、实测数据(prod 只读,2026-10-11)

| 日期 | 懒生成 件/段 | 每件段数 | 懒翻译 次/段 | 每次段数 | 合计段 |
|---|---|---|---|---|---|
| 10-01 | 8 / 64 | 8.0 | — | — | 64 |
| 10-02 | 18 / 141 | 7.8 | — | — | 141 |
| 10-04 | 29 / 222 | 7.7 | — | — | 222 |
| 10-06 | 20 / 153 | 7.7 | — | — | 153 |
| 10-07 | 34 / 245 | 7.2 | 21 / 56 | 2.7 | 301 |
| 10-08 | 35 / 294 | 8.4 | 7 / 21 | 3.0 | 315 |
| 10-10 | 16 / 143 | 8.9 | 3 / 8 | 2.7 | 151 |

(几乎全是运营者账号。)**一次懒生成 ≈ 8 段,一次懒翻译 ≈ 3 段**,两者差近 3 倍。

v1 按"次数"计(生成、翻译各算 1)有两个问题(评审 A 条 + 本表):
1. 单 IP 100 次若全刷新生成 ≈ 800 段 = 全站额度 80% —— 一个 IP 几乎就能让所有人「明天再来」。
2. 同一件切多种语言的真实用户(轻)与刷新件的脚本(重)付同样代价。

## 三、方案:三层上限,统一按"估算段数"计

**计数单位 = 估算段数**,与第 ③ 层同一个单位,三层可以直接比较:
懒生成记 **8**、懒翻译记 **3**(上表实测均值)。

| 层 | 新/旧 | 上限(段/天) | 约等于 | 挡什么 |
|---|---|---|---|---|
| ① 每账号 | 新 | **160** | 20 件新生成,或 50 次翻译 | 一个账号刷;同一 WiFi 下一个人吃掉别人的 IP 额度 |
| ② 每 IP | 新 | **300** | 37 件新生成 | 单 IP 换游客号刷;单 IP 最多吃掉全站 30%,刷光全站至少要 4 个 IP |
| ③ 全站 | 旧 | **1000**(不改) | ~120 件 | 多 IP 分布式;最后的钱包止损 |

- **`can_preview` 运营账号不受 ①② 限制**(仍受 ③)。10-08 运营者一天 315 段,会撞 ②。
- **不再区分游客/正式账号**(评审 D:三档复杂度收益比差)。区分的唯一理由是游客号零成本,
  但游客号的批量来源是同一 IP,已由 ② 管住。
- 真实游客一天打开的未生成件远少于 20 件;博物馆共享 WiFi 下 300 段 = 37 件新生成,同馆多人同日也很难到。
- 数值放常量,看 WARNING 日志再调。

**被拦** → 返回 `unavailable_reason="daily_cap"`(10-10 已有加法字段,App 已会显示「明天再来」,**不改契约、不发包**)。

**② 对分布式攻击无效**(IPv6 地址轮换、住宅代理都能零成本换 IP)。它只挡单 IP 脚本;分布式只有 ③ 兜底。
这是有意的取舍,不是遗漏。

## 四、实现要点

- **原子计数,无竞态**(评审 B:先查后计在 2 个 worker 下会越线):
  拿到锁 → `INCRBY` 账号键和 IP 键各加权重 → 任一结果超上限 → `DECRBY` 回滚两键、清锁、返回 `daily_cap`。
  先加后判是原子的,并发也不会越线。
- **键**:`lazy:u:{user_id}:{UTC日期}`、`lazy:ip:{ip}:{UTC日期}`;每次 `INCRBY` 后都 `EXPIRE 172800`
  (键里带日期,重复设 TTL 无害;避免"只在首次设 TTL"写漏导致永不过期 —— 评审 E)。
- **复用 `recognition/service.py:_get_redis`**(已有连接失败冷却)。
- **Redis 不可用 → 放行 + ERROR 日志**(fail open)。第 ③ 层在 DB 照样兜底;fail closed 会让 Redis 一抖全站懒生成停摆。
  Redis 挂掉期间 ①② 失效且无主动告警 —— 已知,并入 backlog 现有「失败只写日志、不发告警」那条一起解决。
- **IP 来源**:端点加 `request: Request`,取 `request.client.host`。`main.py:104` 的 `ProxyHeadersMiddleware`
  (trusted 127.0.0.1 与 172.16.0.0/12)已把它解析成真实客户端 IP;日志里的 127.0.0.1 是容器内健康检查,不会走内容端点。
- **身份**:`_caller_id`(`museums.py:76`,仅此一处调用)改为返回用户对象(或 None),端点据此传 `user_id`、`can_preview` 给
  `maybe_trigger`(新增可选关键字参数,现有测试全用关键字调用,不受影响)。
- **被拦记 WARNING**:`lazy: cap hit layer=user|ip user=… ip=… used=…`,作以后判断有没有人在刷的证据。
- 只改 `services/enrichment/lazy.py` 和 `api/v1/endpoints/museums.py`。

## 五、写入面

只新增 Redis 计数键(2 天过期)。不写 DB、不碰内容与音频。

## 六、测试

- ①②③ 各自到线被拦,返回 `daily_cap`,且被拦那次已 `DECRBY` 回滚(计数不虚增)、锁已清。
- 权重:生成记 8、翻译记 3。
- `can_preview` 不受 ①②,仍受 ③。
- 没拿到锁(已在生成)不计数。
- **并发**:同一账号两个线程同时点火、各需 8 段、剩余额度只够 1 次 → 只有 1 次成功(评审 B)。
- Redis 抛异常 → 放行,第 ③ 层仍生效。
- 不同 UTC 日期用不同键。
- 匿名(无令牌)仍不点火、不计数(回归)。

## 七、相邻的花钱路径(核过,不在本方案)

- **懒音频**(`/audio`、`/audio/stream`):有 `_require_audio_access` 付费墙(402),只对已发布文本合成。
  新账号免费试听天数(D8)理论上可换号刷,但 TTS 兜底单段约 $0.005,7–10 月共约 $0.5,远低于文本生成。暂不加计数。
- **识别**:有单独的计费与限流(`recognize_billed`、免费 5 次),不归本方案。

## 八、评审意见处理记录(Fable,2026-10-11)

| 意见 | 处理 |
|---|---|
| A「8 段/件」是生成+翻译混合均值,没拆分 | **采纳**。prod 拆分见第二节;计数改为按估算段数加权 |
| B 先查后计有竞态 | **采纳**。改为先 INCRBY 后判断、超了回滚 |
| B ② 对 IPv6/代理无效 | **采纳**,第三节写明 |
| B 127.0.0.1 会误伤 ② | 核实:是健康检查,不走内容端点;`ProxyHeadersMiddleware` 已解析真实 IP |
| C Redis 故障无告警 | **部分采纳**:已知并入 backlog 告警条目,本方案不单独做 |
| D 只做 ②、不做 ① | **不采纳**,但去掉游客/正式分档。理由:①防的是同一 WiFi 下一个账号把整个 IP 的额度吃光、波及同馆其他人,这个只有 ① 能挡;去掉分档后 ① 的复杂度只剩一个数 |
| E 先只记日志观察几天(shadow) | **不采纳**。prod 真实用户极少(识别过的用户共 36 人,懒生成几乎全是运营者),观察几天得不到新信息;默认值来自上表实测,上线后 WARNING 日志照样能用来调 |
| E EXPIRE 只在首次设容易写漏 | **采纳**,改为每次都设 |
